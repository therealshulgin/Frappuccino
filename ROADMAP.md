## §10.7 — Upload JWT en Rust de bout en bout (PUT + report + recovery en Rust), heap-0 — [✅ FAIT + field-validé 2026-06-15]

**Contexte (finding §10.6, validé on-device)** : le JWT d'upload (24 h) survit lock+panic dans le heap JVM. Traité par :
- **combo-1** (`ab314a6`, serveur write-once, **déployé**) — ferme le **PIRE CAS** : un JWT volé ne peut ni lire (403 scope), ni supprimer (pas de route), ni écraser un chunk authentique (write-once → 409). **C'est le fix qui compte.**
- **combo-2** (L1 + `connectionPool.evictAll()`) — JWT en `Zeroizing` côté Rust, en-tête transitoire par-PUT, zeroize + éviction des connexions au lock/panic. Retire les détenteurs applicatifs persistants et réduit le résidu (heap post-wipe **35 → 14**).

**Limite prouvée (2026-06-14)** : le Niveau 1 **ne peut PAS atteindre heap-0**. Dès que le `Bearer` est passé en String à OkHttp, sa couche HTTP/2 (table HPACK + `Headers` par-requête sur la connexion poolée) en garde des copies dans le heap JVM que le code app ne peut pas purger (14 copies **stables** sur 2 dumps, evictAll appliqué). **Résidu accepté** : inoffensif car combo-1 neutralise tout usage d'un JWT volé.

**Calibrage de sévérité (2026-06-14)** : ce résidu relève de l'adversaire « **lecture RAM d'un device vivant déverrouillé, fenêtre étroite** » — **distinct et de moindre portée** que l'adversaire saisie/coercition/destruction que vise le modèle. Il **ne rend pas le modèle caduc** : le témoignage est déjà sur le relais aveugle (chiffré, seul-la-seed-le-ré-ouvre), un JWT lu est neutralisé serveur (write-once + scope), la forward secrecy tient. ⇒ **durcissement / défense-en-profondeur, pas faille critique** ; le Niveau 2 ci-dessous est un objectif de robustesse, **non-bloquant** pour l'audit ou la publication. ## §10.8 — Hébergement-agnostique du contenu (direction, non engagée)

**Principe (déjà vrai aujourd'hui)** : sans la seed, un rush est un blob opaque ⇒ l'hébergeur du **contenu** est interchangeable (Vultr / S3-compatible / self-host / décentralisé / hostile). C'est un choix d'**availability + métadonnées**, jamais de confidentialité. Détail + nuances : `docs/ARCHITECTURE_TECHNIQUE_COMPLETE.md` §8.6.

- **Déjà agnostique** : la couche stockage (MinIO = S3-compatible ⇒ B2/R2/Wasabi/self-MinIO = changement d'endpoint/config).
- **Requiert la logique Frappuccino** : le *control-plane* (auth ratchet, anti-rejeu, monotonie, scope, write-once, TTL) — self-hostable/fédérable, **pas supprimable**.

**Directions, par effort croissant :**
1. **Backend stockage pluggable + documenté** — abstraire l'endpoint S3, qu'un opérateur pointe son propre store. *Faible.*
2. **Multi-homing / redondance** — pousser les mêmes blobs vers N stockages indépendants ⇒ résilience saisie/takedown d'un hôte (gros gain availability, compatible blind). *Moyen.*
3. **Couche blob décentralisée (R&D)** — IPFS/Storj/Arweave pour le **contenu seul**. Caveats : control-plane non mappable ; métadonnées publiques + permanence en tension avec TTL/forward-deletion. *Recherche, pas quick-win.*

**Non urgent, non bloquant** : renforce le positionnement (résilience au takedown) sans changer la garantie, déjà tenue.

## §10.9 — Transport obfusqué pluggable (métadonnée fil, direction — PoC d'abord)

**Contexte** : **Tor recalé** (latence/débit/clunky, incompatible upload vidéo continu — `docs/METADATA_EXPOSURE_MAP.md` §8). Décision 2026-06-14 = transport **pluggable**, couvrir les 3 menaces, **PoC puis affiner**. Cadre = 2 sous-objectifs orthogonaux : **(1) inclassifiable** (résolu par obfuscation) vs **(2) destination non-reliable** (résidu dur).

**Abstraction** (client Rust, trait `Transport` derrière la couche upload) :
- `DirectTls` (actuel, pin SPKI) — défaut/baseline ;
- `ObfQuic` (type **Hysteria2** via `quinn`, vers un endpoint obfusqué self-hosté devant le relais) — **primaire** (BBR ⇒ gain résilience sur réseau lossy = bonus terrain) ;
- `RealityTcp` (**VLESS+REALITY**, TCP/443) — **fallback** UDP-bloqué + meilleure camouflage anti-censure ;
- `Vpn` (« confiance au VPN/AmneziaWG de l'OS ») — option.
Sélection = toggle Settings + fallback auto (UDP→TCP). Côté relais : endpoint obfusqué (sing-box/hysteria/xray) **devant** le relais (blobs déjà E2E ⇒ relaie des octets). Défense-en-profondeur **sous** TLS-épinglé+STRM.

**PoC (gate avant productionisation)** : monter un endpoint Hysteria2/QUIC devant le relais de test + 1 session upload via le toggle ; **mesurer débit vs direct sur réseau normal ET throttlé/lossy** (BBR aide-t-il vraiment ?) + confirmer trafic ~HTTP/3 inclassifiable. Si débit ≥ direct sur mauvais réseau ET inclassifiable → productioniser ; sinon reconsidérer.

**✅ Résultats PoC (2026-06-14, relais de test, lien impairé isolé en netns — relais jamais touché)** — débit **upload** (Mbit/s, plafond = cap netem) :

| Réseau simulé | TCP cubic | TCP BBR | QUIC Brutal (hysteria) |
|---|---|---|---|
| 40 ms / 1 % perte / 20 m | 3.13 | 18.5 | 19.6 |
| 80 ms / 5 % perte / 8 m | 0.62 | 7.07 | 7.87 |
| 150 ms / 10 % perte / 4 m | 0.21 | ~3.3 | 3.89 |

**🔑 Découverte décisive** : le **client Android (Seeker) utilise `cubic`, et BBR n'est PAS disponible** (kernel : reno/cubic only). Or pour l'**upload**, c'est le CC de l'**émetteur** (le téléphone) qui gouverne — pas le BBR du serveur (qui ne sert que le download). ⇒ **notre upload réel = la ligne `cubic` = il s'effondre sous la perte** (≈6 % du plafond à 10 % de perte). Le QUIC/Brutal porte son **propre CC userspace**, **contournant le stack cubic-only d'Android** → **×6 (1 %) à ×15 (10 %)** de goodput vs notre baseline réelle.

**Conclusion** : thèse **fortement confirmée**, mais pour une raison plus fine que « QUIC > TCP » — c'est « **QUIC échappe au cubic-only d'Android qui craque sous la perte** ». ⇒ **DOUBLE gain : fiabilité d'upload terrain** (probable contributeur à la perte de chunks observée en réseau dégradé, cf. data-loss 1.x) **+ obfuscation**. Justifiable sur le seul axe fiabilité ; l'obfuscation devient le bonus. ⚠️ **Caveats** : Brutal était *informé* de la bande passante (meilleur cas — erreur d'estimation réelle à prévoir, mais le gain survit) ; netem loopback ≠ vrai radio (indicatif, direction sûre) ; coût data/batterie des retransmissions sur mobile métré ; PoC nettoyé (netns supprimé).

**2 devices vérifiés (2026-06-14) : Seeker (MTK, Android 16) ET OnePlus 13 (SD8 Gen3, Android 16) = TOUS DEUX en `cubic` par défaut** ⇒ le collapse-sous-perte est **général**, pas device-spécifique. Nuance : BBR est **dispo** sur le OnePlus (kernel `reno bbr cubic`) mais **PAS** sur le Seeker (`reno cubic` only) ⇒ « passer le socket TCP en BBR » **n'est PAS portable** (marcherait sur OnePlus, échoue sur Seeker) → **QUIC (CC userspace) = le seul fix uniforme toutes-devices** (3ᵉ argument pour QUIC : portabilité). **Quick-win interim — faisabilité PROUVÉE on-device (2026-06-14)** : un test `setsockopt(TCP_CONGESTION,"bbr")`+`getsockopt` (compilé NDK arm64, lancé **non-privilégié** uid 2000 sur le OnePlus) → **`bbr` settable et appliqué** (`getsockopt`=`"bbr"`), contrôle négatif `nonexistent_cc` **échoue** (ENOENT) ⇒ mécanisme réel. Implémentation = quelques lignes de **JNI** sur le fd du socket d'upload (OkHttp `SocketFactory` custom) : `try bbr else keep cubic` ⇒ **no-op inoffensif sur Seeker** (bbr absent) + **gain BBR immédiat sur devices BBR-capables**, en attendant QUIC. Reste : élargir la matrice devices.

**Résidu non résolu par l'obfuscation** : *destination non-reliable* (« on voit que tu parles à CET endpoint ») = front CDN partagé / VPN multi-tenant / rotation IP — à trancher selon la menace réelle.
