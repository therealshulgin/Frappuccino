# Transport: obfuscation, pinning & break-glass — Design rationale (adversarial steelman)

> Model: claude-opus-4-8[1m]. Date: 2026-06-28. Scope: the on-the-wire transport for chunk upload — Salamander/QUIC obfuscation, SPKI pinning that bypasses CA validation, the 3-pin break-glass set, the QUIC→DirectTls fallback, and the SNI/domain trade-off — defended choice-by-choice for a state adversary doing DPI + seizure.

This document is a **design defense**, not a vulnerability hunt. For each choice it makes the affirmative case, justifies the specific implementation against the alternatives, states the sharpest hostile objection and either rebuts or concedes it, then names the assumptions and the questions for a future audit. Every claim is cited to the code as read on the `xenodochial-morse` worktree on 2026-06-28.

---

## 1. Scope & the choices under review

The transport layer sits **below** the E2E STRM container (blobs are already ciphertext) and **below** the ratchet auth (the bearer is held inside Rust and never crosses the FFI). Its job is purely: get an opaque ciphertext blob to the relay (a) reliably, (b) without a passive observer being able to classify the traffic as "Frappuccino," and (c) without a CA or a single cert key being a single point of brick or MITM. The concrete choices:

- **ObfQuic as the release transport for both debug AND release.** `RustUploadTransport.mode = TransportMode.OBF_QUIC` (`RustUploadTransport.kt:46`), read live per chunk by `ChunkUploadWorker` (`ChunkUploadWorker.kt:167`).
- **Salamander per-packet XOR obfuscation under QUIC.** `crypto-rs/stream/src/salamander.rs:60-86` (obfuscate/de-obfuscate), wired as an `AsyncUdpSocket` shim in `salamander_socket.rs:53-123`, injected in `quic.rs:440-460`.
- **App-embedded PSK** (obfuscation secret, not a confidentiality key). `quic.rs:130-132` (`prod_target`), held `Zeroizing` in `salamander_socket.rs:32,49`.
- **SPKI pinning that deliberately bypasses CA chain validation.** `pin.rs:1-13` (rationale), the custom `ServerCertVerifier` at `pin.rs:209-288`; the RT-01 real signature check at `pin.rs:250-271`.
- **A 3-pin break-glass set with constant-time union acceptance.** `pin.rs:36,46,62` (the three pins), `pin.rs:186-193` (`spki_matches_any`, OR without early-exit), mirrored in `network_security_config.xml:55-61` + `UploadHttpClient.kt:95-99` + `quic.rs:117-121`.
- **QUIC→DirectTls automatic fallback with a degraded latch.** FFI dispatch `lib.rs:1600-1656`; latch + re-arm in `quic.rs:179-244`.
- **Domain (not raw-IP) SNI, with the SNI/metadata trade-off accepted.** `pin.rs:69` (`PINNED_HOST`), the strict SNI host-check at `pin.rs:219-234`; trade-off documented in `METADATA_EXPOSURE_MAP.md:117` and `TLS_PINNING_ROTATION_RUNBOOK.md:209`.
- **Tor explicitly excluded; obfuscation+pinning chosen instead.** Decision recorded in `METADATA_EXPOSURE_MAP.md:129`.

## 2. Choice-by-choice rationale

### 2.1 ObfQuic as the default transport (debug AND release)

- **What it is.** The chunk PUT runs over `quinn` + `h3` + BBR, with every datagram XOR-obfuscated, targeting the production Salamander de-obfs front on UDP `:8445` which de-XORs and forwards plain QUIC to Caddy on `:8444` (`quic.rs:60-67`). The transport is selected by a single `@Volatile var mode` defaulting to `OBF_QUIC` (`RustUploadTransport.kt:45-46`), read live per chunk (`ChunkUploadWorker.kt:167`).
- **Affirmative case.** This is the "D-1 closure": before this, the release binary spoke plain pinned TLS to the raw relay IP, so a DPI observer saw *that* a Frappuccino-shaped TLS flow existed and *when* the user uploaded (`RustUploadTransport.kt:22-29`). ObfQuic makes the wire look like uniform-random UDP and turns the relay into a dead port for any prober without the PSK — directly serving the motto's "le téléphone est un relais" by making the relay link itself unclassifiable. Shipping the *same* transport in debug and release means the field path is the one that was dogfooded (field-validated on OnePlus CPH2653 + MediaTek, `transport=obfquic`, 0 fallback, 0 error per `RustUploadTransport.kt:27-29`), eliminating a debug-vs-release transport skew.
- **Why this implementation.** Alternatives considered and rejected (`TRANSPORT_PLAN.md`, `METADATA_EXPOSURE_MAP.md:129-159`): plain TLS (classifiable + no loss resilience); VLESS+REALITY (state-of-the-art camouflage but a Go ecosystem — embedding sing-box or re-implementing REALITY is a large non-Rust cost, `METADATA_EXPOSURE_MAP.md:136`); AmneziaWG (full-VPN, but AS-level blocking of some datacenters, `:137`); Tor (latency/throughput incompatible with continuous video upload, `:129`). QUIC wins because (i) `quinn` is Rust → same rustls/UniFFI stack, no new language surface; (ii) BBR in userspace beats Android's cubic-only kernel TCP ×5-15 under loss (`quic.rs:4-6`), so obfuscation is a **net reliability gain**, not a tax; (iii) it fronts a generic HTTP/3 endpoint so the traffic is "ordinary QUIC," not a bespoke framing (`quic.rs:6-11`).
- **Adversarial stress.** *Objection:* "You added a tokio multi-thread runtime + quinn + h3 into the very `.so` that carries the formally-verified sensitive crypto — that is a large new attack surface around your crown jewels, and it is gated by a Cargo feature so the audited artifact may not be the shipped one." *Partial concession:* the audit-surface cost is real and was explicitly made a gate criterion (`TRANSPORT_PLAN.md:213-215,233`). It is mitigated by the heap-0 contract (the bearer never enters this code via FFI, `lib.rs:1581-1598`) and by the blobs being ciphertext before they reach the transport — a quinn/h3 memory bug cannot leak plaintext or the bearer-as-argument. But "QUIC parser bug in the same address space as the ratchet" remains a legitimate thing for an auditor to probe.
- **Assumptions & residual.** Rests on: the production de-obfs front on `:8445` being live and the embedded PSK matching it byte-for-byte (`quic.rs:122-129`). Explicitly does NOT claim to hide *that the user talks to the relay* (destination is still visible, §2.7). **Doc drift to flag:** `StreamPreferences.kt:725-726` still claims "release stays DirectTls via RustUploadTransport.mode's own default" — that is stale; the default is `OBF_QUIC` for release too (`RustUploadTransport.kt:46`). The comment, not the behavior, is wrong, but it could mislead an auditor.
- **Questions for the future audit.** (1) Is the shipped release `.so` actually built with the `quic` feature, i.e. does the audited artifact == the shipped artifact? (2) Does a quinn/h3 fuzz campaign against the de-obfs front surface any memory-safety issue that could pivot toward the ratchet state in the same process? (3) Does the `:8445` front add any logging/correlation the app cannot see?

### 2.2 Salamander per-packet XOR obfuscation

- **What it is.** Each datagram on the wire is `[8-byte random salt][payload XOR keystream]` where `keystream = BLAKE2b-256(PSK ‖ salt)` repeated over the payload (`salamander.rs:7-9,40-67`). De-obfuscation recovers the QUIC packet in place or, on a too-short/garbage datagram, returns `None` → quinn drops it (`salamander.rs:76-86`). It is byte-identical to Hysteria2's salamander so a Go/`sing-box` terminator interoperates exactly (`salamander.rs:5-7`).
- **Affirmative case.** Two precise security goals, both stated honestly as obfuscation-not-confidentiality (`salamander.rs:11-18`): (a) defeat passive QUIC fingerprinting — every packet looks like uniform random bytes, so a DPI box cannot say "this is QUIC" let alone "this is Frappuccino"; (b) the **dead-port property** — a prober without the PSK sends a packet that de-obfuscates to garbage, yields no valid QUIC header, and is silently dropped, so the relay UDP port appears closed to active scanning. This is exactly the "inclassifiable" sub-goal from the metadata work (`METADATA_EXPOSURE_MAP.md:131`).
- **Why this implementation.** Reusing Hysteria2's exact scheme (rather than inventing one) buys interoperability with a mature, audited Go terminator and avoids a bespoke crypto-construction the team would have to defend alone. XOR-with-a-keyed-keystream is the right primitive here precisely *because* the goal is obfuscation: it is cheap (one BLAKE2b per packet), stateless (per-packet salt → no sequence state to desync), and adds only `SALT_LEN` bytes. A heavier AEAD would be miscategorized effort — confidentiality is already provided by the TLS-1.3-inside-QUIC and the STRM layer.
- **Adversarial stress.** *Objection 1:* "XOR with a per-packet keystream derived from a low-entropy, app-shared PSK is trivially reversible by anyone who extracts the PSK from the APK, so this stops nobody who has the binary." *Rebuttal:* conceded and explicitly documented as the threat boundary (`salamander.rs:11-18`, `quic.rs:125-129`) — it is defense against *passive DPI*, not against an adversary holding the APK. The confidentiality guarantee lives in the STRM E2E layer + ratchet, not here. *Objection 2:* "GSO/GRO disabled (`salamander_socket.rs:111-118`) means every datagram is its own syscall — a throughput/battery cost." *Rebuttal:* accepted and bounded as "negligible at the app's mobile-upload packet rate, the only structural throughput effect" (`salamander_socket.rs:7-9`). *Objection 3 (subtle, real):* the salted datagram exceeds the path MTU by 8 bytes; with DF set the kernel silently drops over-MTU packets → a black hole. *Rebuttal:* this was caught and fixed — MTU discovery is capped 8 below quinn's ceiling and the initial MTU floored at 1200 so `1200+8` fits the IPv6 minimum (`quic.rs:573-585`).
- **Assumptions & residual.** Rests on BLAKE2b output being indistinguishable from random (so the XOR'd payload looks random) and on the salt being fresh per packet (`salamander_socket.rs:67`, `OsRng`). Does NOT claim traffic-shape hiding: packet *sizes and timing* still track the recording envelope (the burst-envelope leak, `METADATA_EXPOSURE_MAP.md:66`). An observer who already knows the PSK (APK holder) sees through it entirely.
- **Questions for the future audit.** (1) Is the per-packet salt truly drawn from a CSPRNG on every send path including retransmissions, with no reuse? (2) Does the uniform-random wire actually survive a modern ML/statistical classifier (entropy of QUIC-with-salamander vs. genuine random UDP), or does packet-size/timing distribution still betray it? (3) Does the `debug_assert!` that GSO is off (`salamander_socket.rs:62`) hold in the release `.so` where debug asserts are compiled out — i.e. could a future quinn enable GSO and silently break the per-packet-salt invariant in release only?

### 2.3 App-embedded PSK (obfuscation secret, not a key)

- **What it is.** A 64-hex-char PSK is compiled into `prod_target` (`quic.rs:130-132`), passed to `SalamanderSocket` and held `Zeroizing` (`salamander_socket.rs:32,49`), never printed (`quic.rs:90-99` redacts it in Debug; `salamander_socket.rs:35-40` too).
- **Affirmative case.** A single shared obfs secret is the correct model for the dead-port property: it must be the *same* on every client and the server front, like Hysteria2's obfs password (`salamander.rs:16-18`). Per-user obfs keys would defeat the goal (the server could not de-obfuscate without first knowing who you are, re-introducing identity at the transport).
- **Why this implementation.** Embedding in the binary is the only option that works for a passive-DPI defense that must run *before* any handshake/identity. The honest framing — "an adversary holding the APK can extract it (documented limitation)" (`quic.rs:125-129`) — is the right call: it is categorized as an obfuscation secret, so its extraction degrades obfuscation to nothing but compromises **no** confidentiality. The PSK was rotated 2026-06-27 off the long-lived dev value and is flagged for re-provision at the 8.2.5 public release (`quic.rs:127-129`).
- **Adversarial stress.** *Objection:* "A burned PSK (one APK reverse-engineered) de-anonymizes the whole fleet's transport at once — every Frappuccino user's traffic becomes classifiable the moment one binary leaks, which is the day it ships publicly." *Honest concession:* true and inherent to any shared-secret obfuscation. The mitigation is operational (rotate the PSK per release, `quic.rs:129`) not architectural; a single public APK with a static PSK gives a state adversary a permanent classifier until the next release. This is the strongest honest weakness in the obfuscation story.
- **Assumptions & residual.** Rests on the PSK being fresh at publication and rotated on a cadence. Does NOT claim per-user unlinkability at the transport. The `Zeroizing` is hygiene — the value is in the `.text`/`.rodata` of the shipped binary regardless.
- **Questions for the future audit.** (1) What is the PSK rotation cadence post-launch, and how is a rotated PSK delivered to the field (it requires an APK push — same brick concern as a pin)? (2) Does the server front accept *multiple* PSKs during a rotation overlap, or is PSK rotation itself a flag-day? (3) Is the 64-hex string the raw PSK bytes or a hex-encoding the server decodes — i.e. is the effective keyspace 32 bytes or 64 ASCII chars (parity with the server's `FRAP_OBFS_PSK`)?

### 2.4 SPKI pinning that bypasses CA validation

- **What it is.** A custom `rustls` `ServerCertVerifier` that does NOT walk a trust store; it (1) checks the SNI equals the pinned host (`pin.rs:219-234`), (2) checks the peer leaf's SPKI SHA-256 equals a configured pin (`pin.rs:236-247`), and (3) — the RT-01 fix — actually verifies the `CertificateVerify` signature by delegating to the rustls helpers (`pin.rs:250-271`). The Kotlin side mirrors this with `network_security_config.xml` + an OkHttp `CertificatePinner` (`UploadHttpClient.kt:94-99`).
- **Affirmative case.** The relay uses a self-signed EC P-256 cert no CA signed (`pin.rs:3-13`), so CA validation is meaningless here; pinning the SPKI is *stronger* than CA validation because it removes the entire CA system as a trust dependency. For a state adversary who can compel a CA to mis-issue, "no CA is trusted for this domain" closes that whole class of MITM — the NSC even drops the `system` anchor for the relay domain precisely to shut the window where a state-issued CA could MITM after the pin-set expires (`network_security_config.xml:18-27`). Pinning on the SPKI (not the cert) means cert rotation under a stable key needs no client change (`pin.rs:1-13,81-83`).
- **Why this implementation.** SPKI-on-public-key beats cert-fingerprint pinning (survives renewals) and beats CA pinning (no CA dependency). The RT-01 history is the load-bearing detail: an earlier version returned `Ok(assertion())` from the signature callbacks without verifying, so an MITM re-presenting the *public* pinned cert but signing with its own key would pass the SPKI check — pin-without-signature-check is a classic fail-open. The fix delegates to `verify_tls1{2,3}_signature` with the ring algorithm set snapshotted at construction (`pin.rs:250-271,166`), and is guarded by an end-to-end regression test that drives a real TLS handshake with a forged `CertificateVerify` and asserts `BadSignature` (`pin.rs:494-598`).
- **Adversarial stress.** *Objection 1:* "Rust ignores cert expiry entirely (`_now: UnixTime` unused) — you will accept an expired cert forever as long as the SPKI matches." *Concession:* explicitly true and documented (`TLS_PINNING_ROTATION_RUNBOOK.md:148`); the design accepts it because the threat is brick-not-MITM (an expired-but-pinned cert is still the right key) and there is no CA to honor the expiry anyway. *Objection 2:* "The two enforcing stacks (Rust rustls + Android OkHttp/NSC) can drift — if one is updated and the other isn't, you have an inconsistent trust posture." *Rebuttal:* the `checkRustSoFresh` build gate value-greps every shipped `.so` for every pin declared in `pin.rs` (`build.gradle:58-88`), so a `.so` that dropped a pin fails the build; the cross-stack pin values are asserted in tests against the embedded certs (`pin.rs:372-425`). *Objection 3:* "The NSC pin-set expiration (`2036-05-10`) un-pins one day before the cert expires, then falls back to the embedded anchor + at that point the design has dropped `system`, but an auditor should confirm the post-expiry behavior on real devices." *Concession:* flagged as falsifiable and device-dependent in the runbook (`TLS_PINNING_ROTATION_RUNBOOK.md:144-151,189`).
- **Assumptions & residual.** Rests on the relay private key staying secret (a leaked key → full MITM, since RT-01 means the adversary needs the *private* key, which a leak provides). Does NOT claim CA-grade revocation (there is none). The constant-time pin compare is explicitly "hygiene, not load-bearing" since both operands are public hashes (`pin.rs:182-185`).
- **Questions for the future audit.** (1) Is the RT-01 regression test (`pin.rs:494-598`) actually run in CI on the shipped configuration, and does it still assert `BadSignature` after any rustls bump? (2) Does the NSC post-pin-expiry behavior on the target Android versions (12–16) hard-fail or silently un-pin? (3) Is there any code path (auth, archive, the QUIC front) that builds a TLS client WITHOUT `PinnedCertVerifier`?

### 2.5 The 3-pin break-glass set with constant-time union

- **What it is.** Three SPKI pins — primary `QnGK0K` (live, key backed-up on the relay), live-next `AmIDSg` (the cert the relay currently serves, key on the relay), and off-host `MUb4HH` (key generated off-host and **never** placed on the relay, dormant) (`pin.rs:36,46,62`). The verifier accepts a peer matching ANY pin via an OR over `ct_eq` without early-exit (`pin.rs:186-193`). All three are mirrored in NSC (each self-signed next cert needs its own embedded trust-anchor since the pin is checked *after* chain-to-anchor, `network_security_config.xml:30-61`), OkHttp (`UploadHttpClient.kt:95-99`), and the QUIC prod target (`quic.rs:117-121`).
- **Affirmative case.** This converts every rotation from a flag-day brick into a graceful overlap — the highest-leverage fix the rotation runbook identified (`TLS_PINNING_ROTATION_RUNBOOK.md:232-243`). The genuinely clever part is the **off-host third pin**: both relay-resident keys fall together to a single seizure, so a seizure would otherwise force an emergency APK push (a flag-day that is impossible to do fast). The off-host key, already pinned + anchored in the field but never on the relay, lets the operator stand up a NEW relay, deposit the off-host key, re-point DNS, and the fleet cuts over with **no APK push** (`pin.rs:48-62`, `TLS_PINNING_ROTATION_RUNBOOK.md:18-28`). This is "une saisie n'expose rien" extended to recoverability: a seizure neither exposes content (E2E) nor permanently severs the field.
- **Why this implementation.** A "second pinned key WE control" is repeatedly distinguished from a CA fallback (`pin.rs:44-45,96-98`): adding it does not widen MITM because it is still a key only the operator holds — unlike re-adding the `system` anchor, which would trust any CA. The off-host SAN is the **domain only** (no IP) because the replacement relay's IP is unknown and it is reached by name (`pin.rs:58-61`). The unified-key trick (`AmIDSg` will also back the future LE cert via `certbot --reuse-key`) means the domain/LE cutover needs no pin change (`TLS_PINNING_ROTATION_RUNBOOK.md:16`).
- **Adversarial stress.** *Objection 1:* "Three pins means three keys any of which an MITM could use — you tripled the MITM key surface." *Rebuttal:* two of the three keys are useless to an MITM without their private halves, and the off-host private key is by construction never network-reachable (`pin.rs:48-52`); accepting a union of keys-you-control is strictly a brick mitigation, not an MITM widening (the union-vs-single distinction is tested at `pin.rs:444-447`). *Objection 2:* "The off-host recovery only covers a *seized relay, same domain* — a burned domain (DNS blocked/seized) still needs an APK push." *Concession:* explicitly scoped out (`pin.rs:61`, `TLS_PINNING_ROTATION_RUNBOOK.md:26`) — honest boundary, not a hidden gap. *Objection 3:* "A dormant embedded anchor whose cert is never served is dead weight that an attacker who compromises the off-host backup could activate." *Rebuttal:* activating it still requires standing up a relay that serves that key AND re-pointing the pinned domain's DNS — the pin alone does not let an attacker redirect anyone.
- **Assumptions & residual.** Rests on the off-host private key actually staying off-host and out of the repo (an operational discipline, `TLS_PINNING_ROTATION_RUNBOOK.md:28`). Does NOT claim recovery from a burned domain. The break-glass certs must carry the right EKU/keyUsage to pass NSC chain validation when served (`TLS_PINNING_ROTATION_RUNBOOK.md:16`).
- **Questions for the future audit.** (1) Can the auditor confirm the off-host private key for `MUb4HH` is genuinely absent from the repo, the relay, and any backup that lives on the relay? (2) Does the off-host break-glass cert actually validate when served (EKU/keyUsage/SAN=domain), or will the cutover discover a chain error at the worst moment? (3) Is there a tested rehearsal of the full seizure cutover (new relay + DNS re-point), or only a written runbook?

### 2.6 QUIC→DirectTls fallback with a degraded latch

- **What it is.** Two-level fallback inside Rust, behind the FFI (`lib.rs:1600-1656`): (a) if QUIC has latched "degraded" (it already failed to *establish* this session — UDP-blocked network), skip QUIC and go straight to DirectTls, tagged `directtls_degraded`; (b) otherwise try QUIC, and if it fails to *deliver* (transport error, not a real HTTP response and not the deterministic `file_missing`/`bad_url`), re-PUT the same chunk over DirectTls, tagged `directtls_fallback` (`lib.rs:1637-1652`). The latch is set only on establishment failure (`quic.rs:189-192,331,344`), re-armed at each recording start and on every auth clear (`quic.rs:194-244`). A timeout does NOT latch (the connection established fine) so the next chunk still tries QUIC (`quic.rs:373-385`).
- **Affirmative case.** No data loss is the overriding invariant: a UDP-blocked network must never strand footage on a seizable device, so the chunk rides DirectTls (same bearer, heap-0) rather than failing. The latch avoids re-paying the connect/idle timeout per chunk on a persistently UDP-blocked path (`quic.rs:168-179`), while the re-arm at recording start means a network that recovers gets obfuscation back without an app restart (`quic.rs:194-201`). The careful distinction — latch on *establishment* failure, not on a *per-stream* error — prevents one transient stream reset from evicting the connection the other 5 concurrent workers are happily multiplexing (`quic.rs:246-262`, the "cap-6 retry storm" it avoids).
- **Why this implementation.** Doing the fallback *inside* Rust (not in the Kotlin worker) keeps the bearer heap-0 on both legs and keeps the worker's status-code branches (`200/401/507/5xx`) identical regardless of transport (`lib.rs:1605-1615`). Surfacing `transport_used` in `PutOutcome` (`lib.rs:1562-1570`) and logging it in `StreamMetrics transport=%s` (`ChunkUploadWorker.kt:281-284`) means the fallback is **never silent** — a field test SHOWS whether the wire was obfuscated or fell back to the classifiable direct path.
- **Adversarial stress.** *Objection (the central honest residual, D-1):* "Your fallback re-exposes exactly what obfuscation was supposed to hide: on a UDP-blocked path every chunk goes over plain pinned TLS to the relay, classifiable again — and a state adversary can *force* this by blocking UDP/443, downgrading your whole fleet to the legible transport at will." *Concession:* explicitly owned as a documented residual (`RustUploadTransport.kt:36-40`). The defense is honesty + observability, not prevention: 0 data loss is preserved, and `directtls_degraded`/`directtls_fallback` is surfaced so the operator can see the downgrade happened. There is no `RealityTcp` obfuscated-TCP fallback yet (it was a Phase 3 stub, `TRANSPORT_PLAN.md:198`), so UDP-blocked = unobfuscated today. This is the single sharpest thing for the next audit to weigh.
- **Assumptions & residual.** Rests on the adversary not being able to also block the DirectTls path (if both are blocked, the blob stays on disk and retries — `quic.rs:373-385`). Does NOT claim obfuscation under UDP blocking. A persistently slow-but-alive QUIC path re-pays the per-chunk timeout (bounded, never data loss, intentional, `quic.rs:373-385`).
- **Questions for the future audit.** (1) Can a state adversary cheaply force the unobfuscated downgrade by dropping UDP, and what fraction of field networks already block UDP/443? (2) Is the `transport_used` signal actually monitored in practice, or just logged where no one reads it? (3) Should a high-risk profile *refuse* to fall back (fail-closed: keep the blob on disk rather than send it legibly) — a policy knob that does not exist today?

### 2.7 Domain-vs-IP / SNI trade-off

- **What it is.** The pinned host is the domain `relay.shake-document-protect.org` (`pin.rs:69`), enforced strictly in the SNI host-check (`pin.rs:219-234`). The earlier design pinned a raw IP with no SNI; the cutover to a domain was a deliberate, documented trade-off.
- **Affirmative case.** The domain is the prerequisite for the off-host break-glass recovery (§2.5) — a seized relay is replaced by re-pointing DNS, which is only possible if the field reaches the relay *by name* not by a baked-in IP (`pin.rs:55-58`). It is also the prerequisite for the future LE/DNS migration (`TLS_PINNING_ROTATION_RUNBOOK.md:201-218`). So the domain buys recoverability and migration headroom that raw-IP pinning structurally cannot.
- **Why this implementation.** The alternative (raw-IP pin, no SNI) had a real metadata advantage: no hostname on the wire, so an observer learned only "talks to this IP" not "talks to *Frappuccino*" by name (`METADATA_EXPOSURE_MAP.md:28,82`). Moving to a domain means the SNI string goes out in cleartext in the TLS ClientHello (`TLS_PINNING_ROTATION_RUNBOOK.md:209`, `METADATA_EXPOSURE_MAP.md:117`). The design accepts this because (a) the IP was *always* a visible sink anyway, (b) the obfuscated QUIC path does not expose an SNI to passive DPI the way DirectTls does (the whole packet is XOR'd), and (c) the recoverability gain outweighs adding a name to a destination that was already attributable.
- **Adversarial stress.** *Objection:* "You traded a metadata win (no SNI) for an operational convenience (DNS re-point), making every DirectTls handshake self-identify as `relay.shake-document-protect.org` — a regression for the exact ISP/state observer in your threat model." *Concession:* explicitly a "metadata regression the migration must weigh" (`TLS_PINNING_ROTATION_RUNBOOK.md:209`, `METADATA_EXPOSURE_MAP.md:117`). Mitigations are named but not all implemented: a neutral domain name (partly done — the chosen name is generic, not "frappuccino"), ECH where viable (not near-term, needs a CDN front, `METADATA_EXPOSURE_MAP.md:138`), or keeping IP-pinning for a high-risk profile (not built). On the obfuscated path the SNI is inside the XOR'd QUIC so it does not leak to passive DPI; the leak is real specifically on the **DirectTls fallback** path (§2.6), compounding that residual.
- **Assumptions & residual.** Rests on the domain name being non-self-identifying (the chosen `shake-document-protect.org` is suggestive but not "Frappuccino"). Does NOT claim SNI privacy on DirectTls. The destination IP/domain remains a hard "you talk to the relay" signal regardless (the unresolved "destination non-reliable" residual, `TRANSPORT_PLAN.md:243-245`, `METADATA_EXPOSURE_MAP.md:131`).
- **Questions for the future audit.** (1) On the DirectTls fallback path, does the cleartext SNI `relay.shake-document-protect.org` materially de-anonymize a user vs. the raw IP (is the domain already publicly attributable to this project)? (2) Is the domain registration itself a metadata sink (WHOIS, registrar logs, passive DNS) that ties the project to an identity? (3) Should the high-risk profile pin IP-only and skip the domain, and is that even compatible with the off-host break-glass model?

### 2.8 Tor excluded; obfuscation+pinning chosen

- **What it is.** Tor (and `arti`/Nym/mixnets) is explicitly recalé for this profile (`METADATA_EXPOSURE_MAP.md:129,144,159`); the chosen direction is fast obfuscated transport (QUIC/Hysteria2-style) + SPKI pinning.
- **Affirmative case.** The app's demand is a *sustained continuous video upload*; Tor's variable latency + throughput + clunkiness is incompatible with that (`METADATA_EXPOSURE_MAP.md:129`), and Nym's 5-hop is "too slow for streaming" while its fast 2-hop loses the mixing (`:144`). Obfuscation+pinning gives a fast, predictable, VPN-like path that *also* improves loss resilience (BBR), so it serves the upload workload rather than fighting it. Because the team controls both client (Rust) and relay, and blobs are already E2E, the obfuscated transport is clean defense-in-depth under the pinned TLS + STRM, and is pluggable (toggle direct / QUIC-obf) (`METADATA_EXPOSURE_MAP.md:140`).
- **Why this implementation.** Tor would solve the "destination non-reliable" residual (the hard one — hiding *that* you talk to the relay) via a crowd, which obfuscation does NOT solve (`TRANSPORT_PLAN.md:243-245`). The design consciously prioritizes the achievable sub-goal (inclassifiable) and the upload workload over the unachievable-at-acceptable-cost one (destination-hiding), and parks the destination problem as a separate decision (shared CDN front vs. IP rotation, `METADATA_EXPOSURE_MAP.md:131,156`).
- **Adversarial stress.** *Objection:* "By excluding Tor you keep the worst residual — the destination is always visible, so 'talking to the relay = you are an uploader' stands, and obfuscation only hides the *how*, not the *who-talks-to-whom*." *Concession:* exactly the documented hard residual (`METADATA_EXPOSURE_MAP.md:131,156-159`, `TRANSPORT_PLAN.md:243-245`). The rebuttal is workload-driven (Tor cannot carry the upload) and partial (a future shared front / IP rotation is the named-but-unbuilt answer). For a user whose mere connection to the relay is the risk, obfuscation+pinning is insufficient and the design says so.
- **Assumptions & residual.** Rests on the threat being primarily content + classification + seizure, NOT "the adversary watches who connects to this specific IP." Does NOT claim destination unlinkability. Guardian Project (OHTTP/Orbot) is named as the natural OSS ally for the unsolved part (`METADATA_EXPOSURE_MAP.md:161`).
- **Questions for the future audit.** (1) For the actual field threat profiles, is destination-visibility (which obfuscation cannot hide) the dominant risk, making the Tor exclusion the wrong call for some users? (2) Is there a viable "crowd" front (shared CDN / multi-tenant VPN) that carries continuous upload without re-introducing a trusted middlebox that sees the metadata? (3) Does excluding Tor foreclose a *fallback-of-last-resort* (very slow but unblockable) for users in the most hostile networks?

## 3. Domain coherence & tensions

The choices form a coherent stack with one explicit internal tension and one clean layering principle.

**The layering is clean and load-bearing.** Confidentiality is STRM + ratchet (above), authentication is the ratchet bearer held heap-0 inside Rust (orthogonal), and the transport layer claims *only* (a) reliability (BBR), (b) classification-resistance (Salamander), and (c) MITM-resistance + recoverability (pinning + break-glass). Crucially, every transport-layer control is honest about being *only* its layer: Salamander says "not confidentiality" (`salamander.rs:11`), the PSK says "not a key" (`quic.rs:125`), the pins say "a key we control, not a CA fallback" (`pin.rs:44`). A weaker design would have blurred these; this one does not, which is exactly what makes it auditable.

**The central tension is obfuscation vs. the fallback.** ObfQuic (§2.1/2.2) exists to make the wire unclassifiable, but the no-data-loss invariant (§2.6) forces a fallback to the *fully classifiable* DirectTls whenever UDP is blocked — and a state adversary can *trigger* that downgrade at will by dropping UDP/443. The design resolves this in favor of availability (footage must leave the device) over obfuscation, and makes the downgrade *observable* (`transport_used`) rather than preventing it. That is a defensible priority given the motto ("tout quitte le téléphone"), but it means the obfuscation guarantee is **conditional on the adversary not blocking UDP**, and there is no obfuscated-TCP fallback yet (`RealityTcp` stayed a stub). An auditor should treat "obfuscation holds only when UDP is open" as the precise, honest claim.

**A second, softer tension: the domain cutover (§2.7) re-introduced an SNI metadata leak to enable the break-glass recovery (§2.5).** These two good choices pull against each other on the DirectTls path specifically — the same path the fallback drops to. So a UDP-blocking adversary gets a double win: unobfuscated traffic *and* a self-identifying SNI. On the ObfQuic happy path neither leaks (SNI is inside the XOR'd QUIC), so the tension is localized to the degraded path, which is the right place for the next audit to focus.

**Doc-vs-code drift to clear:** `StreamPreferences.kt:725-726` still describes release as DirectTls-by-default; the code defaults release to `OBF_QUIC` (`RustUploadTransport.kt:46`). Behavior is correct; the comment is stale and should be fixed so it does not mislead a reviewer.

## 4. Top-3 questions this domain hands to the future adversarial audit

1. **Can a state adversary force the unobfuscated, self-identifying downgrade at will?** The QUIC→DirectTls fallback (§2.6) plus the domain SNI (§2.7) mean that simply blocking UDP/443 collapses the whole obfuscation story to a classifiable, name-revealing TLS flow — with no obfuscated-TCP fallback in place. What fraction of real field networks already block UDP, and should a high-risk profile fail-closed (keep the blob on disk) rather than send it legibly?

2. **Is the audited artifact the shipped artifact, and is the obfuscation secret survivable post-launch?** QUIC/Salamander live behind a Cargo `quic` feature in the same `.so` as the formally-verified ratchet (§2.1), and the PSK is a single static app-embedded secret (§2.3) that becomes a permanent fleet-wide classifier the moment one public APK is reverse-engineered. Confirm the release `.so` is built with `quic`, fuzz the quinn/h3 surface for any pivot toward ratchet state, and pin down the PSK rotation/delivery story (it requires an APK push, same as a pin rotation).

3. **Is the off-host break-glass recovery real and rehearsed?** The three-pin model's headline benefit (§2.5) is seizure recovery via an off-host key + DNS re-point with no APK push. Verify the `MUb4HH` private key is genuinely absent from the repo/relay/on-relay backups, that the dormant break-glass cert actually validates when served (EKU/keyUsage/SAN=domain), and that the seizure cutover has been *rehearsed end-to-end* — not just written down — since its first real use would be under maximum pressure.
