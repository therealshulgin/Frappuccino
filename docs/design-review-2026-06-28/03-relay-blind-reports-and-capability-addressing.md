# Relay-blind reports & capability addressing — Design rationale (adversarial steelman)

> Model: claude-opus-4-8[1m]. Date: 2026-06-28. Scope: how a report is named, authorized, isolated, and enumerated on a blind relay — the at-rest `identity → report → when` join, and why a capability address replaces an account model.

This is a design-defense, not a vulnerability hunt. For each choice it makes the affirmative case, justifies the specific implementation against the alternatives, states the sharpest hostile objection, and then either rebuts it with code evidence or concedes it as a known residual. Every claim is grounded in the source at `file:line`.

The governing motto: *tout quitte le téléphone & une saisie n'expose rien ; le téléphone est un relais, pas un coffre.* For this domain that translates into one at-rest property: **seizing the relay disk must reveal no `identity → which reports → when`.** The reference spec is `docs/RELAY_BLIND_REPORTS.md` (v3, implemented + deployed 2026-06-26).

---

## 1. Scope & the choices under review

The concrete design choices in this domain, each with its anchor:

- **C1 — `report_id = SHA-256("stream.report.id.v1" ‖ report_pk)[..16]` as a self-authenticating capability address** (`crypto-rs/core/src/report.rs:113-121`; relay mirror `server/app/routes/upload.py:23-24`; bind check `upload.py:115-116`).
- **C2 — Per-report independent keys `report_sk_n` derived from a dedicated HKDF context, for unlinkability** (`report.rs:65-74`, `:208-217`, `:224-236`).
- **C3 — Capability addressing instead of an account/owner model** (record schema `server/app/routes/reports.py:18-31`, `:106`; the dropped `owner`/`author`/`createdAt` per `RELAY_BLIND_REPORTS.md:38-52`).
- **C4 — Identity proven once at creation, then DISCARDED** (`upload.py:129-170`, esp. the `del payload`/`sub` flow `:148-170`).
- **C5 — Blob-first lazy creation: a record is written only after ≥1 durable blob** (`upload.py:83-103`, `:176-239`; `reports.py:87-122`).
- **C6 — Domain-separated capability signatures `0x07 ReportCreate` / `0x08 ReportWrite`** (`crypto-rs/core/src/signature_domain.rs:93-98`; mirror `server/app/signature_domain.py:36-37`; relay verify `upload.py:143-147`, `:195-202`).
- **C7 — The report directory for an exact `n_max`, with the M-1 opaque-name decision and its honest residual** (`report.rs:82-99`, `:282-350`; rescue `stream-crypto/.../ArchiveSession.kt:85-164`; writer `mobile/.../DirectoryEntryWorker.kt:106-137`).
- **C8 — The creation budget (anti-sybil), a count never a map** (`server/app/ratchet_registry.py:247-313`; `upload.py:150-170`, `:240-247`; `config.py:47-54`).

## 2. Choice-by-choice rationale

### C1 — `report_id = H(report_pk)` as a self-authenticating capability address

- **What it is** (`report.rs:113-121`, `upload.py:23-24`, `:115-116`). The report's relay-facing address is the first 128 bits of `SHA-256("stream.report.id.v1" ‖ report_pk)`. The relay does not assign it; the client derives it from the per-report public key, and at every PUT the relay re-computes `H(presented report_pk)` and rejects the request unless it equals the URL's `report_id` (`upload.py:115-116`, `HTTPException(400, "report_id does not match X-Report-PK")`). The path component is locked to exactly 32 lowercase hex (`upload.py:31`, `archive.py:44`), so it decodes unambiguously to the 16 bytes the signatures cover.

- **Affirmative case.** The address is *self-authenticating*: it is a cryptographic commitment to the key that controls the report, so the relay never has to maintain an `address → owner` table to know who may write. This is exactly what the motto demands — the relay holds `report_id → report_pk` (`reports.py:106`) and nothing else, so a disk seizure yields no name, no account, no "when". The id is also *re-derivable from the phrase alone* at rescue (`report.rs:228-236`), which is what makes identity-free recovery possible on a blank device.

- **Why this implementation.** The alternatives were (a) a server-assigned random id, (b) the raw `report_pk` as the address, or (c) a hash of identity+counter.
  - (a) requires the server to remember the binding and to be trusted to keep it; it also forces a `create_report` round-trip, which the design explicitly removed (`RELAY_BLIND_REPORTS.md:121`). A server-assigned id cannot be re-derived offline at rescue.
  - (b) using the 32-byte pk directly as the address would work but doubles the URL length and, more importantly, *publishes the pk in the path* on every read — the relay would then index reads by the full pk. The 16-byte hash is a compact, opaque handle that still binds to the pk via the on-PUT check.
  - (c) hashing identity in would re-introduce the very linkage the domain is built to destroy.
  The 128-bit width is the deliberate floor: large enough that the address is unguessable (a read capability), small enough for a clean 32-hex URL (`report.rs:60-61`).

- **Adversarial stress.** *"`H(report_pk)` truncated to 128 bits — can an attacker find a second `report_pk'` that hashes to the same `report_id` and hijack a report?"* Rebuttal: that is a **second-preimage** on SHA-256 truncated to 128 bits. Truncated-SHA-256 second-preimage resistance is ~2^128; the design names this explicitly (`upload.py:113-114`: "makes substituting a different report_pk a second-preimage problem on SHA-256"). And even a found collision is inert: the attacker would still need the corresponding `report_sk'` to produce a valid `write_sig` under their `report_pk'` (`upload.py:201-202`), and a *different* pk against an *existing* record is rejected with 409 (`upload.py:126-127`). So the truncation weakens *unguessability* of the address to 128 bits (fine for a capability), not the *authority* over the report, which rests on Ed25519.

- **Assumptions & residual.** Rests on SHA-256 second-preimage resistance at 128-bit truncation and on the relay actually performing the `H(report_pk) == report_id` check on every write path (it does: `upload.py:115`). It does **not** claim the address is secret from a network observer — anyone who sees a PUT/GET learns that `report_id`. It is a *capability* (possession = read access, `archive.py:13`), so the security argument is "unguessable + unlinkable", never "confidential in transit beyond TLS".

- **Questions for the future audit.**
  1. Is the `H(report_pk) == report_id` check truly on **every** mutating path, including the directory writes (which reuse the same `upload_file` handler)? Confirm there is no second write entry point that skips `upload.py:115`.
  2. Is 128 bits the right width given that a `report_id` doubles as a *read capability* (a leaked id streams ciphertext, `archive.py:68-88`)? The ciphertext is E2E-useless, but is 128-bit guessing-resistance with a 600/min rate limit (`archive.py:69`) sufficient against a determined scanner over a 6-month retention window?

### C2 — Per-report independent keys (unlinkability)

- **What it is** (`report.rs:65-74`, `:208-217`, `:224-236`). From the same BIP-39 seed, a *dedicated* HKDF chain: `report_master = HKDF(seed, "stream.report.master.v1")` then `report_sk_n = Ed25519_seed(HKDF(report_master, "stream.report.key.v1" ‖ u32_be(n)))`. Each report index `n` gets an independent Ed25519 keypair; `report_pk_n` and `report_id_n` for different `n` are unrelated to the relay (`report.rs:410-425` proves distinctness, including byte-boundary indices `256`, `0x0100_0001`).

- **Affirmative case.** Because each report is addressed by an *independent* key, the relay sees a set of mutually-unlinkable `report_id → report_pk` rows. Two reports from the same witness look like two reports from two strangers. This is the at-rest unlinkability the motto needs: even reconstructing the full `reports.json` yields no clustering by author. The keys are also *deterministic from the phrase* (`report.rs:394-399`), so the witness can re-derive every report on a fresh device with no server-side list.

- **Why this implementation.** Alternatives: (a) one report key reused across all reports, (b) per-report keys stored in a local table, (c) deriving report keys from the *identity* key.
  - (a) would make all of a witness's reports trivially linkable by a shared pk — the opposite of the goal.
  - (b) a local table is device state that a seizure of the *phone* exposes and that does not survive to a rescue device; the derivation approach keeps zero per-report secret state (`report.rs:154-164`: only the 32-byte `report_master` is held, mlock'd, wiped on drop).
  - (c) deriving from the identity key would cryptographically tie reports back to the identity. The dedicated HKDF context is the explicit firewall: a distinct context yields a distinct key from identity/provenance/ratchet from the *same* seed (`report.rs:65-74`, asserted `report.rs:401-407`). This mirrors `ProvenanceSigner`'s two-level derivation (`report.rs:19-24`), a pattern already field-proven in this codebase.

- **Adversarial stress.** *"All report keys share one `report_master`; if `report_master` leaks (heap dump of an unlocked device, coercion), every past and future report is linkable and forgeable."* Honest concession: **yes**, `report_master` is the linkage root, and a seized *unlocked* device or a successful heap extraction collapses the unlinkability. This is consistent with the documented threat boundary — the domain defends the **relay at rest**, not a seized unlocked phone (`RELAY_BLIND_REPORTS.md:30`, `:154`; MEMORY: R-D-1/2 = risk-accepted device-dependent). The mitigations are real but partial: `report_master` is `LockedSecret` (mlock'd, zeroed on drop, `report.rs:163-164`, `:189-195`), per-index `report_sk_n` is transient and `Zeroizing` (`report.rs:206-217`), and the master is PIN-sealed at rest. The forward-secrecy claim of the ratchet does **not** extend to reports: report keys are static per index, so a master compromise is retroactive across all reports.

- **Assumptions & residual.** Rests on HKDF-SHA256 context separation and on `report_master` confidentiality (PIN-seal + mlock + zeroize). Does **not** claim per-report *forward secrecy* (a master leak is retroactive) and does **not** claim unlinkability against a network observer who watches two uploads from the same IP/session (that is the live-correlation residual, `RELAY_BLIND_REPORTS.md:147`).

- **Questions for the future audit.**
  1. Verify the lifecycle claim: is `report_master` (via the Rust `REPORT_SK_HOLDER`) actually wiped at lock and never re-derivable without the PIN, and does it correctly survive background/screen-off recording without lingering past the post-stop drain (`RELAY_BLIND_REPORTS.md:96-102`)? A wipe-too-early loses chunks; a wipe-too-late widens the heap-extraction window.
  2. The `u32` index space: the tests guard against truncation/aliasing (`report.rs:423-424`), but is there any client path that could derive the *same* `n` for two distinct sessions (collapsing two reports into one key)? See C5/C7 on the `sessionId → n` atomic mapping.

### C3 — Capability addressing instead of an account/owner model

- **What it is** (`reports.py:18-31`, `:106`). A record is the minimal `{report_id, report_pk}` — "deliberately NO owner, NO author, NO createdAt, NO title" (`reports.py:24-25`). Authorization to write is "do you hold the key that hashes to this address", proven per-request by a signature, not "are you the logged-in owner of this account".

- **Affirmative case.** An account model needs a durable `identity → resources` table — precisely the join the adversary wants. Capability addressing dissolves it: authority travels *with the request* (the signature), so the relay needs no standing record of who owns what. The historical `owner=pk` + `author=pk[:32]` + `createdAt` fields (`RELAY_BLIND_REPORTS.md:39-41`) were the entire at-rest leak, and capability addressing is what let them be removed wholesale (`RELAY_BLIND_REPORTS.md:139`).

- **Why this implementation.** The alternative — keep accounts but encrypt the owner column — was rejected because the relay must *use* the owner to authorize, so it would need the key at request time anyway, and an encrypted-at-rest column still leaks the *number* and *grouping* of an identity's reports. Capability addressing removes the column rather than hiding it: there is nothing to decrypt because there is nothing stored. This also collapses the read path to identity-free (`archive.py:13`): no `list_user_reports`, no archive-scope JWT (`archive.py:21-24`).

- **Adversarial stress.** *"Capabilities are bearer tokens — if a `report_id` leaks (logs, a shoulder-surfed URL, a subpoena of an intermediary), anyone can read or append to the report."* Rebuttal on *append*: writing requires a valid `write_sig` under `report_sk_n`, which a leaked id does not grant (`upload.py:201-202`); write-once storage (`upload.py:218-226`) further blocks overwriting existing chunks. Concession on *read*: a leaked `report_id` does grant download of the **ciphertext** — and this is explicitly accepted (`RELAY_BLIND_REPORTS.md:150`: "qui obtient un report_id télécharge le ciphertext (inutile sans la phrase)"). The downloaded blob is the sealed STRM container, useless without the BIP-39-derived keys (`archive.py:70-75`). So the capability grants *ciphertext read*, which the E2E layer makes inert; it does not grant plaintext or write authority.

- **Assumptions & residual.** Rests on the read capability being benign because content is E2E-sealed, and on the relay never logging `report_id` next to anything identifying. Does **not** claim the `report_id` is unleakable; it claims a leak is bounded to anonymous ciphertext access + rate-limited DoS (`RELAY_BLIND_REPORTS.md:150`, `archive.py:60`, `:69`).

- **Questions for the future audit.**
  1. The log-scrubbing claim is load-bearing for C3/C4: confirm no path logs `report_id` together with the creation JWT's `sub` (the one transient moment identity and report co-exist, `upload.py:148-149`). The spec flags the exception/`repr` channel as historically missed (`RELAY_BLIND_REPORTS.md:44`, `:183-190`).
  2. Is there any intermediary (nginx, MinIO, a proxy) that records the `report_id` in an access log? The spec asserts `nginx access_log off` and untagged MinIO (`RELAY_BLIND_REPORTS.md:190`) — verify against the deployed config, not the doc.

### C4 — Identity proven once at creation, then DISCARDED

- **What it is** (`upload.py:129-170`). Only the *creating* chunk carries `Authorization: Bearer <stream JWT>`. The relay verifies the JWT (`upload.py:137-139`), checks scope (`:140-142`), reads `sub` for the anti-abuse budget (`:148`, `:162-170`), and `del payload` (`:149`) — the identity is used for the reservation and then dropped; it is never written into the record (`reports.py:106` stores only `{report_id, report_pk}`) and the spec is explicit it is "never written to disk" (`upload.py:158-160`).

- **Affirmative case.** This is the hinge that lets the relay enforce *enrollment* (anti-sybil gate) without *retaining* identity. The JWT proves "a real enrolled witness is creating this", which the budget needs; discarding `sub` immediately means the at-rest state never holds the `identity → report` edge. It threads the needle between "open relay anyone can flood" and "account relay that remembers who".

- **Why this implementation.** Alternatives: (a) no identity at all on creation (pure capability), (b) bind a ratchet slot per report.
  - (a) removes the anti-sybil gate entirely — anyone could mint unbounded reports (`RELAY_BLIND_REPORTS.md:175`). The budget (C8) needs *some* enrolled identity to count against.
  - (b) was explicitly rejected: a ratchet slot per report couples creation to a network op, breaks the heap-0/streaming contract, and exhausts the 50-slot batch (`RELAY_BLIND_REPORTS.md:175`). Using the already-held stream JWT as the gate is free.

- **Adversarial stress.** *"At creation time the relay simultaneously holds the JWT `sub` (= the pk) AND the `report_id`. A relay operator who logs that one request, or dumps RAM at T, learns `identity → report`."* Honest concession: **yes**, this is the documented transient (`RELAY_BLIND_REPORTS.md:147`: "1er PUT porte le JWT (sub=pk) ⇒ serveur voit pk à T"). It is a *live*/in-RAM exposure, not at-rest: `sub` is `del`'d (`upload.py:149`), never persisted with the report, and the budget stores only a *count* (C8). The residual is "a relay that actively wiretaps the creation moment" — which is the live-correlation axis the design openly does not close (relay, not vault). The honest mitigation is that it is one request, identity is dropped within the handler, and the spec mandates never logging `sub` next to `report_id` (`upload.py:159-160`).

- **Assumptions & residual.** Rests on (i) the relay actually discarding `sub` (code: `del payload` at `upload.py:149`, no write of `sub` anywhere after) and (ii) no log/exception capturing the pair. Does **not** claim protection against a relay that is actively malicious *at the moment of creation* — only against the *disk at rest* and against passive later inspection.

- **Questions for the future audit.**
  1. Trace every use of `payload`/`sub` after `upload.py:137` to confirm `sub` reaches *only* the budget reservation and is never logged, returned, or stored — including inside `reserve_report_creation`/`release_report_creation` (which take the pk as `ed25519_pk_hex`, `ratchet_registry.py:247`, `:289`, and key the registry by it — see C8 residual).
  2. The budget is keyed by the **full pk** in the registry (`ratchet_registry.py:278-283`). So "discarded" means "discarded *from the report*", not "absent from the relay". Audit whether the registry's `report_creations` map can be correlated with `reports.json` by timing (`updated_at` vs MinIO `last_modified`).

### C5 — Blob-first lazy creation (record ⇒ ≥1 durable blob)

- **What it is** (`upload.py:83-103`, `:176-239`; `reports.py:87-122`). There is no `create_report` endpoint. A report is born on its first chunk PUT, and the ordering is strict: stream + hash the body (`upload.py:177-186`), verify the write-sig (`:195-202`), **store the blob durably** (`:204-226`), and only *then* write the record (`:228-232`, `reports.py:create_or_verify_report`). A "subsequent" chunk that arrives before its creating chunk gets `425 "retry, not yet created"` and stores nothing (`upload.py:128-133`). An empty body is rejected before any record (`upload.py:189-191`).

- **Affirmative case.** The invariant "a record implies ≥1 durable blob" (`upload.py:99-103`) is what makes the rescue's `404-on-unknown-record` *reliable without a `createdAt` or an empty-report sweep*. Removing `createdAt` removes a "when" field; removing the empty-report sweep removes a GC job and the zombie-record class it cleaned up (`RELAY_BLIND_REPORTS.md:81`, `:178-179`). It is a clean way to get the at-rest minimalism (no timestamp) *and* a sound rescue contract from the same ordering rule.

- **Why this implementation.** The earlier design recorded a provisional record first, then stored, then rolled back on failure — which created record-zombies and a 2-worker race (`RELAY_BLIND_REPORTS.md:238`, V2-A1). Blob-first inverts it: a crash between store and record leaves a *blob orphan*, not a *record zombie* (`upload.py:94` in spec / `reports.py:136-155`). An orphan is invisible to rescue (no record ⇒ 404) and reaped by `blob_cleanup` on `last_modified` TTL — strictly safer than a zombie (which would make rescue believe a report exists with no content). Write-once storage makes the store idempotent under the 2-worker race (`upload.py:218-226`), and `create_or_verify_report` converges under the single lock (`reports.py:95-122`).

- **Adversarial stress.** *"Blob-first means an orphan blob (ciphertext) can outlive any record, and the record write can still fail after a durable blob exists — does this lose data or leak?"* Rebuttal on **leak**: an orphan is anonymous ciphertext with a `last_modified` timestamp — the same residual class as any stored blob (`RELAY_BLIND_REPORTS.md:151`), reaped at TTL. Rebuttal on **loss**: if `create_or_verify_report` fails to persist, it rolls back the in-memory insert and raises (`reports.py:107-121`), the PUT 500s, the client retries; the blob is already durable so a retry finds it and just re-writes the record — no loss (`reports.py:111-119`). The honest sharp edge the spec itself flags: dropping `createdAt` removes only a *redundant* "when" — the creation time still leaks via MinIO `last_modified` (`reports.py:142-148`, R-SRV-7). So this is "we keep no extra timestamp", not "the when is sealed".

- **Assumptions & residual.** Rests on write-once storage being genuinely idempotent for byte-identical re-PUTs and conflicting for different bytes (`upload.py:218-226`), and on the single-worker deployment (`reports.py:30-31`) plus the lock making `create_or_verify` race-free. Does **not** claim to seal the upload time (MinIO `last_modified` remains, an anonymous timeline). Does **not** prevent orphan blobs; it makes them benign.

- **Questions for the future audit.**
  1. The reserve-then-release budget interacts with blob-first: a creation that stores a durable blob but then 500s on the record write — does it correctly *keep* the reserved slot (record durable) or *release* it (record not durable)? Trace `creation_committed` (`upload.py:238`) vs the `create_or_verify` failure path (`reports.py:107-121` raises, so `creation_committed` stays False and the `finally` releases — but the blob is durable and a retry will re-create). Confirm a retried creating-PUT after a record-write failure does not double-charge the budget.
  2. `reap_blobless_reports` lists blobs outside the lock and deletes records under it (`reports.py:156-185`). Confirm the benign-window argument (a 6-month-dead report won't receive new chunks) holds against a witness who re-derives an old index and re-uploads.

### C6 — Domain-separated capability signatures `0x07` / `0x08`

- **What it is** (`signature_domain.rs:93-98`, `report.rs:126-147`). Two one-byte domain tags: `0x07 ReportCreate` signs `report_id(16) ‖ report_pk(32)`; `0x08 ReportWrite` signs `report_id(16) ‖ filename ‖ sha256(body)(32)`. The tag is prepended to the message before signing (`signature_domain.rs:113-118`) and the relay prepends the same byte before verifying (`upload.py:143-147`, `:195-202`). Create authorizes the lazy creation (binds id↔pk); write rides every chunk (binds id↔name↔body-hash).

- **Affirmative case.** Domain separation prevents any cross-protocol or cross-operation signature replay: a `create_sig` can never be replayed as a `write_sig` even over coincidentally-equal bytes (`report.rs:487-504` proves both directions fail). The fixed-width `report_id` prefix and `sha256` suffix anchor the variable-length `filename` in the middle unambiguously (`report.rs:35-37`) — no length-confusion forgery. This closes the exact class the Fable 5 audit flagged as "separation depends on length" (`signature_domain.rs:5-11`), the R-C-1 finding, by making separation *explicit* rather than emergent.

- **Why this implementation.** Alternatives: (a) no tags, rely on distinct keys + distinct message shapes, (b) separate keys for create vs write.
  - (a) was the pre-R-C-1 state, flagged as a forgery surface waiting for the next length change (`signature_domain.rs:7-11`). The create message (48 B) and write message (16 + name + 32 B) could collide in length for a short filename, so distinctness was not guaranteed.
  - (b) two keys per report doubles derivation and the create/write pair would no longer share one `report_pk` the relay can pin. Using one `report_sk_n` with two domain tags keeps a single capability key per report while making the two operations non-interchangeable. The tags slot into the existing 1-byte scheme (`0x01`–`0x06` already in use, `signature_domain.rs:62-98`), so it is consistent house discipline, not a new mechanism.

- **Adversarial stress.** *"The Rust signer and the Python verifier are two independent implementations of the byte layout — a one-sided drift (a context string, a tag value, a field order) would silently break or, worse, weaken verification, and the usual diff-fuzz corpus is Kotlin↔Rust, not Rust↔server."* Rebuttal: this exact gap is named and closed by a **cross-language KAT** — `report.rs:608-680` pins `report_pk`/`report_id`/`create_sig`/`write_sig` byte-for-byte and `server/tests/test_report_sig_kat.py` verifies the same bytes against the server's reconstructed messages (`report.rs:613-621`). A change to the context, the tags, the layout, or the derivation breaks one side's test. The signature-domain tags are also pinned stable (`signature_domain.rs:126-147`) and mirrored in `signature_domain.py:36-37`. This is a genuine, tested two-sided contract.

- **Assumptions & residual.** Rests on the KAT being run in CI on both sides (the repo has no remote / CI is dormant — MEMORY notes the CI caveat), and on `verify_strict` / libsodium `crypto_sign_open` agreeing on Ed25519 malleability. Does **not** by itself defend against a relay that simply *skips* verification — that is an operator-trust question, not a signature-scheme one.

- **Questions for the future audit.**
  1. Confirm the server's Ed25519 verify (`auth.verify_detached_ed25519`, `upload.py:146`, `:201`) is strict / non-malleable to match dalek's `verify_strict` (`report.rs:374`) — a malleability mismatch would let a third party mutate a captured signature into a second "valid" one.
  2. The KAT closes Rust↔server *parity*. Is it actually executed in the deployment pipeline (given no remote CI)? A drift caught only by a never-run test is not caught.

### C7 — The report directory for exact `n_max` + the M-1 opaque-name decision and its residual

- **What it is** (`report.rs:82-99`, `:282-350`; `ArchiveSession.kt:85-164`; `DirectoryEntryWorker.kt:106-137`). A singleton, phrase-derived report (its own HKDF context `stream.report.directory.v1`, `report.rs:82`) whose blob *names* are the allocated indices. The device appends one tiny entry per session at index allocation (`DirectoryEntryWorker.kt:55-67`, `:106-121`; body is a constant `0x01`, no index, per `RELAY_BLIND_REPORTS.md:109`). At rescue, the device fetches the directory's blob list and re-derives the entry names to recover `n_max` *exactly*, then probes `0..n_max` densely (`ArchiveSession.kt:148-158`) — a 404 is a skipped hole, never an early stop.
  - **M-1**: the entry name is *not* the plain decimal index `%010d` but an opaque token `directory_entry_name(n) = HKDF(report_master, "stream.report.directory.entry.v1" ‖ u32_be(n))[..16]` (`report.rs:99`, `:321-329`). It is derived from the **secret** `report_master`, never from the public `directory_pk` (`report.rs:88-98`), and the rescue dual-reads legacy `%010d` entries for forward-compat (`ArchiveSession.kt:97-131`).

- **Affirmative case.** Without an authoritative `n_max`, rescue would have to *guess* where to stop (a hole-tolerance constant K), which silently truncates recovery when a run of allocated-but-never-uploaded indices (failed recordings) sits between two real reports (`DirectoryEntryWorker.kt:18-32`). The directory makes enumeration *exact and dense*, closing the benign trous-milieu truncation. Crucially it is built from the *same* relay-blind primitives: to the relay it is just another `report_id → report_pk` (`report.rs:78-82`), unlinkable to identity, write-once append-only (so the mutable-vs-write-once tension is avoided, `RELAY_BLIND_REPORTS.md:167`). M-1 then removes the directory's *fingerprint*: a plain `%010d` name would mark the directory as a session counter and hand a relay operator `n_max`/cadence at a glance (`report.rs:84-98`). The opaque name is indistinguishable from any other blob and, being secret-derived, *unenumerable by the relay* (which sees `directory_pk` but not `report_master`).

- **Why this implementation.** Alternatives considered and rejected:
  - **Guess with hole-tolerance K** — truncates on K+ consecutive holes (the original F5 problem, `RELAY_BLIND_REPORTS.md:111`). Replaced by exact derive-and-match.
  - **A mutable manifest blob holding `n_max`** — conflicts with write-once and needs overwrite semantics; the append-only directory recovers `n_max` by derive-and-match over names instead (`RELAY_BLIND_REPORTS.md:167`).
  - **Chaining entries (Merkle/linked list) to detect drops** — explicitly not added because a hostile relay drops the chained queue *together* with its tail, so chaining detects only middle-drops, which dense enumeration already renders harmless (`RELAY_BLIND_REPORTS.md:167`).
  - **Name = `HKDF(directory_pk, …)`** — rejected because the relay holds `directory_pk` (`X-Report-PK` header) and could re-derive every name and recover each index (`report.rs:89-95`). Secret-derived names close this.
  - **Body carries the index (old 4-byte BE)** — re-leaked count/cadence; replaced by a 1-byte constant since the rescue only reads the *name* (`report.rs:309-317`, `RELAY_BLIND_REPORTS.md:109`).

- **Adversarial stress.** Two sharp objections.
  1. *"The directory aggregates every session of a witness under ONE `report_id`. A relay operator who identifies that one report (by temporal correlation) reads the **number of sessions** (entry count) and their **cadence** (`last_modified`) — at rest."* **Honest concession** (the explicit M-1 non-claim, `RELAY_BLIND_REPORTS.md:114`): the opaque names remove the trivial fingerprint (no readable counter, index unreadable from the name), but a *correlated* operator still learns count + cadence. What it does **not** expose is identity or content (E2E, no pk at rest). The strict motto — "a seizure exposes nothing" = no identity, no testimony — holds; the residual is metadata (how many, how often) for an already-identified directory. `last_modified` coarsening was considered and not adopted (cost/benefit, `RELAY_BLIND_REPORTS.md:114`).
  2. *"A hostile relay can 404 the last directory entries, under-reporting `n_max`, and silently truncate the most recent reports."* **Honest concession** = residual C1 (`RELAY_BLIND_REPORTS.md:113`, `:163`, `ArchiveSession.kt:74-79`): a single untrusted relay can always retain the most recent data (the tail entry as well as its chunks); a chained directory would be dropped with its tail, so this is undetectable with a single relay. The real defense is multi-relay / off-host backup (roadmap 1.8) — out of scope here. The *benign* middle-hole case is fully closed by dense enumeration.

- **Assumptions & residual.** Rests on (i) the secret-derivation of entry names actually using `report_master` not `directory_pk` (code: `report.rs:325` derives from `with_master_bytes`), (ii) the rescue's dense probe truly skipping holes rather than stopping (code: `ArchiveSession.kt:151-158`, a 404 → null → not added, loop continues), and (iii) the derive-and-match cap `DERIVE_MATCH_CAP` (`ArchiveSession.kt:251`) bounding only local hashing, never the network probe, so a relay injecting a junk name cannot DoS the rescue. Does **not** claim to defend against tail-truncation by a single hostile relay (C1) and does **not** hide session count/cadence from an operator who has *already* identified the directory report.

- **Questions for the future audit.**
  1. The directory aggregating all sessions under one id is the single most linkable object in the design. Can an operator identify the directory report among all `report_id → report_pk` rows? It is the only report whose blob names are all the *same length* (32 hex) AND that keeps growing on a regular cadence — does that traffic shape distinguish it from content reports (whose names are `<sid>_NNNNNN.strm`, `upload.py:42`)? If so, the M-1 fingerprint reduction may be weaker in practice than at rest.
  2. Forward-compat dual-read parses legacy `%010d` and opaque names; the schemes are asserted disjoint (a 32-hex never parses as Int, `report.rs:560-568`). Confirm the legacy ceiling (`DERIVE_MATCH_CAP`, `ArchiveSession.kt:109-110`) cannot let a coerced relay inflate `n_max` with one big decimal into a huge dense probe (rescue DoS) — and that the CLI (`fetch_archive.rs`) classifies identically (u32 vs Int).

### C8 — The creation budget (anti-sybil): a count, never a map

- **What it is** (`ratchet_registry.py:247-313`, `upload.py:150-170`, `:240-247`, `config.py:47-54`). The creating PUT proves enrollment with a stream JWT; the relay atomically *reserves* one slot via `reserve_report_creation(sub, MAX_REPORTS_PER_BATCH)` (`upload.py:164-169`), keyed by the identity's *current* `batch_number`, and *releases* it (`upload.py:240-247`) if the upload fails to produce a durable record. The stored state is a *count* per `(identity, batch_number)` (`ratchet_registry.py:278-283`), never a `report ↔ identity` map. Default ceiling 256 (`config.py:54`).

- **Affirmative case.** Without a gate, "identity discarded" (C4) would also discard any durable quota, so a sybil could mint unbounded reports (`RELAY_BLIND_REPORTS.md:175-177`). The budget restores a quota *without* re-introducing the join: counting against the enrolled identity's batch is the same residual class as the existing ratchet `consumed_indices` (numbers, gross activity), not a card of which report belongs to whom (`ratchet_registry.py:265-268`). A per-IP budget was rejected as Tor/botnet-circumventable (`RELAY_BLIND_REPORTS.md:176`), so the per-identity count is the meaningful anti-abuse surface (with per-IP rate-limit as defense-in-depth, `archive.py:60`, `:69`, `upload.py:60`).

- **Why this implementation.** Alternatives: (a) per-IP budget, (b) a ratchet slot per report, (c) peek-then-commit.
  - (a) circumventable (above).
  - (b) couples creation to a network op and exhausts the batch (`RELAY_BLIND_REPORTS.md:175`) — same reason C4 rejected it.
  - (c) the original `can_create_report` peek + later `note_report_creation` commit had a check-vs-commit TOCTOU: under the single async worker, the body stream + `to_thread` store between peek and commit let concurrent creating PUTs all read `count < max` before any committed, making the cap soft (`ratchet_registry.py:251-257`, R-SRV-3). The fix is atomic reserve (check + increment under one lock, `ratchet_registry.py:274-286`) + release on failure (`:289-313`), so the cap is a hard wall and a failed creation never burns budget. `MAX_REPORTS_PER_BATCH` is generous on purpose (a batch ≈ 50 auth slots ≈ many sessions, `config.py:50-53`).

- **Adversarial stress.** *"The budget is keyed and persisted by the full identity pk in the registry, and `report_creations: {batch_number → count}` accumulates per identity over time — that is a dated per-identity activity curve at rest, the very kind of metadata the domain claims to remove."* Honest concession + mitigation: the per-identity pk **is** a documented at-rest residual (`RELAY_BLIND_REPORTS.md:46-47`, the enrollment registry holds pk + counters, "a number, not a card"). The *unbounded growth* objection (M-2) was real and is **fixed**: `rotate_batch` now drops the previous batch's counters (`ratchet_registry.py:232-238`), so only the current batch's count is retained, not a historical curve. What remains is "this enrolled identity created N reports on its current batch" — gross activity, no link to *which* reports. The honest sharp edge for the next audit: this count + `updated_at` (`ratchet_registry.py:284`) could be *timing-correlated* with `reports.json`/MinIO `last_modified` to re-derive a coarse `identity → created-a-report-around-T` signal, even though no explicit edge is stored.

- **Assumptions & residual.** Rests on the registry pk being an accepted residual (the relay must know enrolled identities to gate at all) and on the atomic reserve/release correctly conserving the count under concurrency (`ratchet_registry.py:274-313`). Does **not** claim to hide the *existence* of an enrolled identity or its gross creation activity; claims only that no `report ↔ identity` map is stored.

- **Questions for the future audit.**
  1. Reserve/release conservation: under concurrent failing + succeeding creating PUTs for the same identity, does the count always equal the number of *durable* records (no leak, no double-charge)? Trace the `finally` (`upload.py:240-247`) against every early-return/raise between reserve (`:164`) and commit (`:238`), including the record-write failure (`reports.py:107-121`).
  2. Timing correlation: how tightly can `report_creations`' `updated_at` (or the registry file's mtime) be aligned with `reports.json` mutations or MinIO `last_modified` to reconstruct the discarded `identity → report@T` edge? This is the sharpest residual of C4+C8 together.

## 3. Domain coherence & tensions

The choices form one coherent strategy: **replace the standing `identity → resources` account table with per-request capabilities derived from the phrase, so the relay holds the minimum (`report_id → report_pk`) and the witness re-derives everything else.** C1 (self-authenticating address) + C2 (independent keys) + C6 (domain-separated sigs) give *authority without an owner column*; C3 + C4 + C5 strip the at-rest fields (owner/author/createdAt) that were the entire leak; C7 buys back *exact rescue* without a server-side list; C8 buys back *anti-sybil* without a durable join. Each "buy-back" is deliberately implemented to stay in the same residual class as something the relay already holds (the enrollment registry's numbers), never to re-create the forbidden edge.

Internal tensions worth flagging for the next audit:

- **The directory is the linkability concentrator.** Everything else is per-report-independent (C2), but C7 deliberately aggregates *all* sessions under one phrase-derived id to enable exact enumeration. M-1 opaque names reduce the at-rest fingerprint, but the directory is the one object that, if identified, yields count + cadence. This is the price of exact rescue, consciously paid (`RELAY_BLIND_REPORTS.md:114`). It is the natural focus for the next audit's traffic-analysis lens.

- **Identity is "discarded" but not "absent".** C4 drops `sub` from the *report*, yet C8 keys the budget by the full pk in the registry, and the registry pk is an accepted residual. So the relay still knows *who is enrolled* and *roughly how active* — the line the design draws is "no `report ↔ identity` map", not "no identity". The sharpest residual is the *timing join* between the (kept) registry counters and the (kept) MinIO `last_modified` / `reports.json`, which together could approximate the discarded edge without it being explicitly stored.

- **At-rest vs live is a hard boundary, repeatedly.** Blob-first removes `createdAt` but `last_modified` remains (C5); identity is discarded but visible at the creation instant (C4); reports are unlinkable at rest but correlatable by IP/session live (C2). The domain is internally consistent in defending *the disk at rest* and openly conceding *the live/active-relay axis* — multi-relay/Tor is named as the only real defense for the conceded parts (`RELAY_BLIND_REPORTS.md:154`, C1).

- **Two-implementation crypto contract.** The Rust signer / Python verifier split (C6) is the one place a silent drift could weaken authority; it is guarded by a cross-language KAT, but the dormant-CI caveat means the guard's *execution* should be confirmed, not assumed.

## 4. Top-3 questions this domain hands to the future adversarial audit

1. **Can the report directory be singled out among all `report_id → report_pk` rows, and if so what does it leak?** It is the one object that aggregates every session under one id and grows on a cadence. M-1 opaque names defeat the *at-rest* fingerprint, but a traffic-shape / growth-pattern analysis (constant-length names, regular append cadence, distinct from `<sid>_NNNNNN.strm` content names) may re-identify it operationally, exposing session count + cadence for a witness. This is the conceded M-1 residual (`RELAY_BLIND_REPORTS.md:114`) and the domain's single biggest linkability concentrator.

2. **How tightly can the kept metadata be timing-joined to reconstruct the "discarded" `identity → report@T` edge?** C4 discards `sub` from the report and C8 fixed the unbounded-counter growth, but the relay still retains, per enrolled pk, a current-batch creation count with `updated_at` (`ratchet_registry.py:284`), alongside MinIO `last_modified` and `reports.json` mutation times. A correlation of these timestamps could approximate the very edge the design removed from explicit storage — the sharpest at-rest residual of C4+C8 together.

3. **Is the Rust↔server signature contract (C6) and the `H(report_pk)==report_id` bind (C1) actually enforced on every path and verified by an *executed* test?** The KAT (`report.rs:608-680` ↔ `test_report_sig_kat.py`) and the on-PUT bind check (`upload.py:115`) are the load-bearing guarantees, but the repo has no remote CI; confirm (a) every mutating entry point routes through the bind check and write-sig verify (including directory writes), (b) the server's Ed25519 verify is strict/non-malleable to match dalek, and (c) the cross-language KAT is run in the actual deployment pipeline rather than existing as a never-run guard.
