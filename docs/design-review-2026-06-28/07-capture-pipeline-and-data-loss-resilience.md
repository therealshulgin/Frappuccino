# Capture pipeline & data-loss resilience — Design rationale (adversarial steelman)

> Model: claude-opus-4-8[1m]. Date: 2026-06-28. Scope: the HEVC chunked stream-encrypt-upload-delete pipeline, the upload queue + circuit breaker + 507 disk-full handling, the data-loss trio (idempotent report / zombie sweep / dedup) + the no_auth_token fix, adaptive quality cap, and secure-delete's honest limits.

This document is a design *defense*, written to feed a later adversarial audit. For each choice it makes the affirmative case, justifies the implementation against the alternatives, states the sharpest honest objection and either rebuts or concedes it, then lists what an auditor should probe. The motto governs everything: *tout quitte le téléphone & une saisie n'expose rien ; le téléphone est un relais, pas un coffre.*

---

## 1. Scope & the choices under review

- **Stream-and-delete chunking** rather than record-then-upload: capture 5 s MP4 chunks, encrypt each to a standalone `.strm`, secure-delete the plaintext immediately. `RollingChunkRecorder` (`stream-crypto/.../capture/RollingChunkRecorder.kt:57`), `onChunkReady` (`StreamRecordingService.kt:1608`), `StreamChunkEncryptor.encryptChunk` (`stream-crypto/.../capture/StreamChunkEncryptor.kt:57`).
- **Plaintext never crosses the JVM heap**: Rust opens the MP4, encrypts, writes the `.strm` (`StreamChunkEncryptor.kt:64` → `strmEncryptFile`).
- **Each chunk is independently decryptable** (no cross-chunk chaining): `StreamChunkEncryptor.kt:18-24`.
- **Crash-durable upload queue** in `filesDir` (survives cache clear), with a directory `fsync` after rename: `ChunkUploadQueue.kt:22,57-118`.
- **Idempotent capability PUT + write-once relay**: `ChunkUploadWorker.doWork` (`ChunkUploadWorker.kt:79`), keyed by phrase-derived `report_id` + `0x07/0x08` sigs (`crypto-rs/core/src/report.rs:123-264`).
- **Circuit breaker** (consecutive-5xx + half-open probe gate + stuck-probe timeout): `UploadCircuitBreaker.kt:34`.
- **507 disk-full handling**: immediate circuit-open + `Result.retry()` never `failure()` (`ChunkUploadWorker.kt:228-237`, `UploadCircuitBreaker.kt:186-195`).
- **Adaptive concurrency cap** with FIFO fairness + `pendingShrink` debt: `UploadConcurrencyLimiter.kt:32`.
- **Adaptive quality ladder** (down fast, up slow) with user-configurable max cap: `AdaptiveQualityManager.kt:47`, `StreamQuality.kt:83`.
- **Data-loss trio**: idempotent per-session report index (`StreamPreferences.allocateReportIndexForSession`, `StreamPreferences.kt:432`), zombie/orphan sweep with bounded give-up (`OrphanSweepWorker.kt:84`), dedup via `enqueueUniqueWork(blob.name, KEEP)` (`StreamRecordingService.kt:2254`, `OrphanSweepWorker.kt:383`).
- **no_auth_token fix**: defer the JWT auto-clear while encryptions are in flight (`V2LockTimeoutController.kt:152`, `StreamRecordingService.encryptionsInFlight()` `StreamRecordingService.kt:156-160`).
- **48 h TTL sweep + in-app loss alert** (no system notification): `ChunkUploadQueue.sweepStaleChunks` (`ChunkUploadQueue.kt:189`), `StreamPreferences.addOrphanDeletion` (`StreamPreferences.kt:577`).
- **Secure-delete as defense-in-depth, FBE as the real defense**: `crypto-rs/stream/src/secure_delete.rs:24-48`.

## 2. Choice-by-choice rationale

### 2.1 Stream-and-delete chunks vs record-then-upload

- **What it is.** Capture is split into 5 s MP4 chunks by `RollingChunkRecorder` (`RollingChunkRecorder.kt:57`); each finished chunk is delivered to `onChunkReady` (`StreamRecordingService.kt:1608`), encrypted to a standalone `.strm` and the plaintext MP4 is secure-deleted in the same call (`StreamChunkEncryptor.kt:57-97`). The `.strm` goes to a `filesDir` upload queue and is removed after a successful PUT.
- **Affirmative case.** This is the motto rendered as a pipeline. A record-then-upload design keeps a full plaintext recording on disk for the entire session; a seizure mid-recording (or right after, before manual upload) hands the adversary the whole testimony. Stream-and-delete bounds the plaintext lifetime on disk to roughly one chunk window (~5 s + encryption latency) and bounds the *encrypted* residue to the upload backlog, which the pipeline actively drains. The phone genuinely becomes a relay: footage leaves continuously and the local copy is destroyed continuously.
- **Why this implementation.**
  - *Chunk size 5 s.* Long enough to amortise per-chunk MediaCodec/muxer setup and keep one IDR per chunk (`buildHevcVideoConfigFor` sets `keyframeIntervalSec` = chunk seconds, `StreamRecordingService.kt:1384`), short enough that the on-disk plaintext window and the "lose the in-flight chunk on crash" blast radius stay ~5 s. A single continuous `MediaRecorder` was rejected because it can't deliver incremental, independently-uploadable, independently-decryptable units.
  - *Independently decryptable chunks* (`StreamChunkEncryptor.kt:18-24`): if the stream cuts after N chunks, chunks 1..N are all recoverable from the BIP-39 phrase. A single chained stream-cipher container would make a truncated upload undecryptable — the opposite of resilience.
  - *Plaintext never on the JVM heap* (`StreamChunkEncryptor.kt:62-68`): Rust does `File::open` + `Zeroizing<Vec<u8>>`; the prior `chunkFile.readBytes()` copied plaintext into JVM heap for ~10 ms, a live-dump window. The `encryptChunk` path also secure-deletes the plaintext in a `finally` (`StreamChunkEncryptor.kt:84-95`) so an encryption *failure* still destroys the MP4.
  - *Continuous pipeline across chunk boundaries* (`RollingChunkRecorder` keeps camera/GL/PCM live, recreates only the per-chunk muxer+codec; `RollingChunkRecorder.kt:20-35`): preallocates the next chunk's encoder `preallocLeadMs` ahead (`RollingChunkRecorder.kt:179,544`) so the rotation seam is ~10 ms, not a visible gap.
- **Adversarial stress.** *"You've multiplied the secure-delete surface: every 5 s you create then destroy a plaintext MP4 on flash. On a wear-levelled NAND the overwrite doesn't hit the original cells, so you've sprinkled hundreds of recoverable plaintext fragments across the partition instead of one."* — **Partial concession, with the real defense named.** The code is explicit that overwrite-on-flash is best-effort and that **FBE (file-based encryption) is the actual line of defense** (`secure_delete.rs:30-40`): an adversary without the device key reads ciphertext regardless of freelist residue. So the fragments are FBE-ciphertext, not plaintext, against the in-scope adversary (seizure of a locked device). Secure-delete only matters in the narrower "adversary already has the device key / live RAM forensics" branch, where it shrinks (not eliminates) the recoverable set. The multiplication objection is real *only* in that branch and is consciously accepted there.
- **Assumptions & residual.** Rests on: FBE being active (Android 10+ standard); the camera HAL actually delivering finalized chunk files (a flaky HEVC encoder is handled by the H.264 fallback, `RollingChunkRecorder.kt:476`); and the in-flight chunk at a hard crash being acceptable loss (~5 s). Does NOT claim plaintext is unrecoverable on a key-compromised device.
- **Questions for the future audit.**
  1. What is the *true* maximum plaintext-on-disk window under load (encryption-thread backlog at `onChunkReady`, `StreamRecordingService.kt:1623-1672`)? If encryption threads pile up, multiple plaintext MP4s can coexist briefly — quantify it.
  2. Is there any path where a chunk MP4 is finalized but `onChunkReady` never runs (so it's never secure-deleted)? The `cacheDir/stream_chunks` cleaner only purges 0-byte files (`CaptureScratchCleaner.kt:112`), not non-empty orphaned plaintext.

### 2.2 Crash-durable upload queue (`filesDir` + directory fsync)

- **What it is.** `.strm` blobs live in `filesDir/stream_chunk_queue` (`ChunkUploadQueue.kt:22`), not `cacheDir`, so the OS cache-clear can't evict pending evidence. `enqueue` renames the blob in and then `fsync`s the *directory* fd (`ChunkUploadQueue.kt:98-114`).
- **Affirmative case.** Pending evidence is data the user expects to upload; losing it to a routine cache purge or a power-loss-during-rename would be silent data loss. The directory fsync (Audit R-06) closes the ext4 `data=ordered` window where the blob's data blocks are durable but the parent directory entry still lives in the journal — a forced shutdown then leaves the ciphertext on the partition as an *orphan* invisible to `listFiles()`, which means neither panic-wipe nor the secure-delete sweep can target it (`ChunkUploadQueue.kt:45-56`). So the fsync is both a durability *and* a hygiene measure.
- **Why this implementation.** `renameTo` is used as the fast path; a cross-partition rename failure (observed on some custom ROMs / Samsung A-series, `ChunkUploadQueue.kt:59-69`) falls back to copy + secure-delete of the source so the original `.strm` (whose `nonce_prefix`/`session_id` pattern is forensically correlatable) disappears too. A naive `File.delete()` fallback would leave that correlatable source behind.
- **Adversarial stress.** *"You fsync the directory but not the blob file's data before the rename — and the `getPending` cache (TTL 1 s, `ChunkUploadQueue.kt:127-142`) can hand a worker a path that a concurrent `sweepStaleChunks` already secure-deleted."* — **Rebuttal, mostly.** The blob is written + closed by the encryptor before `enqueue` is even called (`onChunkReady` enqueues only after `encryptChunk` returns a file, `StreamRecordingService.kt:1643-1647`), so the data is already flushed by the encryptor's close; the directory fsync is specifically for the rename's metadata. The stale-cache race is benign by construction: the worker treats a missing/zero-length blob as success (`ChunkUploadWorker.kt:112-115`) and the Rust PUT returns `file_missing` → success (`ChunkUploadWorker.kt:174-177`). Cache mutations all call `invalidateCache()` (`ChunkUploadQueue.kt:115,163,212,241`).
- **Assumptions & residual.** Rests on `android.system.Os.fsync` actually flushing on the device's filesystem (best-effort; failure is logged non-fatal, `ChunkUploadQueue.kt:112-114`). Does NOT guarantee the *blob bytes* survive a power-loss in the encryptor's own write (that's the encryptor's `writeBytes`/`strmEncryptFile`, not fsync'd by this queue).
- **Questions for the future audit.**
  1. Is the blob file's own content fsync'd before `remove()` deletes the plaintext source? If `strmEncryptFile` (Rust) doesn't `sync_all` the output, a power loss could leave a partial `.strm` *and* a deleted plaintext = total loss of that chunk.
  2. The 1 s `getPending` cache is read on the main thread (`ChunkUploadQueue.kt:24-33`) — confirm the cache can never return a list that drives a *second* enqueue of an already-removed blob into a fresh report.

### 2.3 Idempotent capability PUT + write-once relay

- **What it is.** Every chunk is a `PUT /file/{report_id}/{filename}` where `report_id` is phrase-derived (not identity) and the body carries domain-separated Ed25519 sigs (`0x07` create, `0x08` write) signed inside Rust from the live `ReportKeyring` (`report.rs:123-264`, `ChunkUploadWorker.kt:157-169`). Seq 0 (metadata) is the lazy *creation* PUT; seq ≥ 1 are pure writes.
- **Affirmative case.** Idempotency is the backbone of data-loss resilience: because the address is `report_id` + filename and the relay is write-once on identical bytes, re-uploading the same chunk after a crash, a retry, or a duplicate enqueue is a safe no-op. This is what lets every failure path choose `Result.retry()` over `Result.failure()` without risk of duplication or corruption. It also serves the motto directly: the relay stores `report_id → report_pk`, never `identity → report`, so a relay seizure reveals no link (`report.rs:1-8`).
- **Why this implementation.**
  - *Lazy creation (425 handshake).* WorkManager doesn't order workers, so a write (seq ≥ 1) can reach the relay before its creation PUT (seq 0). The relay answers **425** and the worker retries (`ChunkUploadWorker.kt:191-202`) — chosen over client-side ordering (which would serialize the whole upload and kill parallelism) and over server-side auto-create (which would let a stray write mint a record under the wrong key).
  - *Capability over identity.* The worker carries only the derivation index `n`, never the `report_id` or any secret, so the persisted WorkManager `Data` (stored in clear in `androidx.work.workdb`) can't leak a report↔identity handle (`ChunkUploadWorker.kt:60-76`). The id and sigs are re-derived in Rust at PUT time — heap-0.
  - *Domain-separated sigs* (`SignatureDomain::ReportCreate`/`ReportWrite`, `report.rs:132,145`): a create-sig can never be replayed as a write-sig and vice-versa; cross-language KAT pins the exact bytes against the Python relay (`report.rs:653-680`).
- **Adversarial stress.** *"`Rust-only by construction` means a single broken native binding bricks ALL uploads — there's no fallback transport. One bad `.so` ABI and every chunk loops forever."* — **Honest concession, with the design reason.** This is a deliberate trade (`ChunkUploadWorker.kt:294-312`): the capability headers *are* the FFI, so any break that disables the binding also disables signing; an OkHttp fallback couldn't sign and the relay-blind relay rejects identity-based uploads anyway. The chosen failure mode is "retry forever, blob preserved on disk, 0 loss until a healthy build runs" rather than "fail and drop." The residual is real: a permanently-broken build + the 48 h TTL = data loss. The mitigation is the all-ABI build discipline (per project memory, `.so` regen across arm64/armv7/x86_64) and the diff-fuzz parity gate — both *process* controls, not runtime ones.
- **Assumptions & residual.** Rests on the relay being genuinely write-once on differing bytes (a 4xx ≠ 401/425/429 is treated as permanent, blob left on disk, `ChunkUploadWorker.kt:221-227`) and on the cross-language sig layout never drifting (KAT + diff-fuzz). Does NOT claim resilience against a build whose `.so` is missing for the device ABI.
- **Questions for the future audit.**
  1. The 429 creation-budget path retries forever on the assumption the per-batch counter self-heals on ratchet rotation (`ChunkUploadWorker.kt:203-220`). If a device never rotates its batch (e.g. recording without consuming auth slots), can a creation chunk starve permanently → every later chunk stuck on 425 → 48 h TTL loss?
  2. A permanent 4xx (bad sig / write-once conflict on differing bytes) is `Result.failure()` and leaves the blob on disk (`ChunkUploadWorker.kt:221-226`) — but nothing re-attempts it. Confirm the orphan sweep eventually re-enqueues it under a *correct* index, or it's silent loss-until-TTL.

### 2.4 Circuit breaker (consecutive-5xx, half-open probe gate, stuck-probe timeout)

- **What it is.** A process-singleton that counts global consecutive 5xx; at threshold 3 it opens for 60 s, then allows exactly one half-open probe via a CAS gate, with a 90 s stuck-probe timeout (`UploadCircuitBreaker.kt:34-137`).
- **Affirmative case.** Without it, a backlog of 100+ chunks built up during an outage all re-hit the relay the instant it returns, re-knocking it over (and burning ephemeral ratchet auth slots for nothing). WorkManager's per-worker exponential backoff doesn't coordinate *across* workers; the breaker is the global coordinator (`UploadCircuitBreaker.kt:6-33`). This protects both the relay (a shared, single point) and the device's scarce auth-slot budget.
- **Why this implementation.** The half-open probe gate (Blue HIGH-5, `UploadCircuitBreaker.kt:74-83`) was added because the naive "cooldown elapsed → everyone sees CLOSED" let N queued workers tap a still-down server simultaneously, each consuming an auth slot. The single-probe CAS lets exactly one worker test the water; the others stay closed-from-their-perspective until it reports. The stuck-probe 90 s timeout (Blue HIGH-5, `UploadCircuitBreaker.kt:52-60`) prevents a worker killed mid-PUT from blocking the gate forever.
- **Adversarial stress.** *"It's process-local in-memory state. A locked-device adversary can't touch it, but it also means a process restart resets the breaker to CLOSED and a freshly-woken backlog stampedes again — and the `@Synchronized` methods on the WorkManager thread pool could serialize uploads under contention."* — **Rebuttal.** The reset-on-restart is intentional and documented (`UploadCircuitBreaker.kt:23-26`): a cold start is a fresh opportunity, and a real outage will simply re-open the breaker after 3 errors (~3 PUT attempts, bounded). The synchronization is on cheap state transitions, not the PUT itself (the PUT happens outside any breaker lock, between `isOpen()` and `reportSuccess`/`reportServerError`), so it doesn't serialize transfers.
- **Assumptions & residual.** Rests on WorkManager running in the main process (so the singleton is shared). Does NOT protect across multiple app processes (none exist today). The disk-full 507 path piggybacks on the same state with a 5 min cooldown (see 2.5).
- **Questions for the future audit.**
  1. Threshold 3 / cooldown 60 s are global across *all* workers — under a large orphan-sweep batch, could a few genuinely-bad chunks (permanent 4xx that don't touch the breaker, but transient 5xx that do) interact to keep the circuit flapping and starve good chunks?
  2. The breaker counts a transport error (`code == 0`) as a server error (`ChunkUploadWorker.kt:245-255`) — a purely local network blip thus opens the circuit globally. Is that over-eager (one device's lost wifi pauses all its uploads for 60 s even if the relay is fine)?

### 2.5 507 disk-full handling (retry-never-fail + immediate open + 5 min cooldown)

- **What it is.** On HTTP 507 the worker opens the circuit immediately (no threshold wait) for a longer 5 min cooldown and returns `Result.retry()` — never `failure()` (`ChunkUploadWorker.kt:228-237`, `UploadCircuitBreaker.kt:186-195`). `isDiskFull()` drives a user-facing "serveur plein" notification.
- **Affirmative case.** This is the purest expression of "never drop evidence." A full relay disk is not the witness's fault and not transient-on-retry-timing; mapping 507 to `failure()` would discard the chunk. Instead the blob stays on-device and uploads once an admin frees space (or the relay's own TTL purges old data). The immediate open (no 3-error wait) avoids hammering a server physically unable to store anything.
- **Why this implementation.** A distinct 5 min cooldown (vs 60 s for transient 5xx, `UploadCircuitBreaker.kt:41-49`) because a disk doesn't free itself in 60 s. The user notification matters: the witness needs to know their evidence is *stuck*, not *gone*, so they can act (contact admin / change relay).
- **Adversarial stress.** *"Retry-forever + on-device blob retention means a malicious or compromised relay can deliberately 507 to force evidence to accumulate on the device — defeating the relay-not-vault motto and growing the seizure surface."* — **Partial concession.** True: a relay that always 507s pins the evidence on the phone until the 48 h TTL secure-deletes it (the backstop). So the motto degrades gracefully to "everything *tries* to leave; if the relay refuses, the device holds it for ≤48 h then destroys it and tells the user." A coercion-aware witness can panic-wipe to destroy immediately. The residual is the 48 h on-device retention window under a hostile relay — accepted, bounded, and surfaced to the user.
- **Assumptions & residual.** Rests on the relay honestly returning 507 (a relay could instead silently 200-and-discard, which the client can't detect — a verification gap). Does NOT defend against a relay that lies about storage.
- **Questions for the future audit.**
  1. Is there any client-side confirmation that an accepted (2xx) chunk was actually persisted by the relay (e.g. a later directory/archive read-back)? Without it, a relay can ack-and-drop and the client believes the evidence is safe.
  2. The "serveur plein" notification requires a foreground/visible surface; during covert recording the app declares no notification permission (`StreamPreferences.kt:553-558`). How does a covert-mode witness learn their uploads are stuck?

### 2.6 Adaptive concurrency cap (FIFO fairness + pendingShrink debt)

- **What it is.** A semaphore-backed cap that auto-tunes 1..6 from a rolling median of upload times, with fair FIFO acquisition (45 s wait) and a `pendingShrink` debt counter so a cap-shrink that can't reclaim in-flight permits converges later (`UploadConcurrencyLimiter.kt:32-330`).
- **Affirmative case.** On a slow uplink, 4 parallel PUTs each get a quarter of the bandwidth, turning a 5 s chunk into a 25 s upload and compounding the backlog; capping gives each PUT a meaningful share. The 45 s FIFO wait (Phase 3.48, `UploadConcurrencyLimiter.kt:63-95`) fixes a real field starvation: a worker that missed the old 5 s window re-entered WorkManager's exponential backoff (10→20→40→80 s) and the *oldest* chunk starved ~57 s while everything else drained — i.e. the resilience mechanism was itself causing loss-by-delay.
- **Why this implementation.** Fair semaphore + long wait keeps a waiter *queued on the semaphore* instead of leaving and re-arriving behind a doubled backoff. The `pendingShrink` debt (Blue CRIT-1, `UploadConcurrencyLimiter.kt:107-120,162-186`) fixes a silent drift where `repeat(-delta){ tryAcquire() }` no-op'd when all permits were busy, leaving `availablePermits()` permanently above the cap — defeating the cap on borderline networks. `bumpCapForRecovery` (Phase 3.49, `UploadConcurrencyLimiter.kt:237-255`) breaks a 14 min field deadlock where cap stayed at 1 after a cellular→wifi switch because the only growth path needed fresh successful samples that cap=1 starved.
- **Adversarial stress.** *"A 45 s permit wait holds a WorkManager pool thread (default ~4-8). Under cap=1 + a large backlog, another job (Enrollment, OrphanSweep) can wait up to 45 s for a thread — you've traded chunk starvation for cross-job starvation."* — **Concession, bounded.** The code acknowledges exactly this (`UploadConcurrencyLimiter.kt:88-93`): worst-case permit hold is acquire(≤45 s) + PUT(≤120 s) ≈ 165 s, within WorkManager's ~10 min budget, and OrphanSweep self-gates to empty while the service runs. The `acquireWait` metric (`UploadConcurrencyLimiter.kt:144-158`) was added to measure this retention in the field. It's a measured, bounded trade, not an unbounded risk.
- **Assumptions & residual.** Rests on WorkManager's pool being large enough that a few held threads don't deadlock other critical work. Does NOT claim optimality — it's a median-driven heuristic with `SAMPLE_WINDOW=8` hysteresis.
- **Questions for the future audit.**
  1. Can a pathological link (every PUT takes 44.9 s, just under the 45 s wait) hold all pool threads indefinitely while making forward progress one chunk at a time, blocking enrollment/auth?
  2. `bumpCapForRecovery` is monotonic-up only and resets samples — could a flapping link repeatedly re-arm to cap=2 and wipe the window often enough to prevent the cap from ever settling to the link's true capacity?

### 2.7 Adaptive quality ladder + user max-quality cap

- **What it is.** Per-chunk upload-time ratio drives quality up/down with asymmetric hysteresis (3 down, 10 up), a backlog-freeze on upgrades, a forced backlog-downgrade, a 60 s anti-yo-yo cooldown, and a VBR↔CBR mode ladder (`AdaptiveQualityManager.kt:47-512`). A user-set `maxQuality` clamps the ceiling (`StreamQuality.coerceAtMost`, `StreamQuality.kt:83`; `AdaptiveQualityManager.kt:84,405`).
- **Affirmative case.** Resilience = the upload keeping pace with capture. If chunks upload slower than they're produced, the backlog grows unbounded → 48 h TTL loss. Dropping quality shrinks per-chunk bytes so the queue drains; the asymmetry (react fast to degradation, recover slowly) avoids quality yo-yo that itself wastes bandwidth on rebuilds. The user cap lets a field user bound per-chunk size and data usage on a metered/flaky link while the adaptive logic still drops *below* the cap as needed (`AdaptiveQualityManager.kt:74-84`).
- **Why this implementation.** Every constant is field-derived and documented: `FAST_HYSTERESIS` raised 5→10 after HD chunks re-accumulated post-reconnect (`AdaptiveQualityManager.kt:423-437`); `FORCE_DOWNGRADE_BACKLOG` lowered 10→6 because the downgrade fired too late (`AdaptiveQualityManager.kt:447-457`); the 60 s anti-yo-yo cooldown after a Seeker session oscillated ~55 s (`AdaptiveQualityManager.kt:494-511`). The forced backlog-downgrade breaks a deadlock where cap=1 + concurrency-capped workers never report upload times so the SLOW path never triggers (`AdaptiveQualityManager.kt:150-161`).
- **Adversarial stress.** *"The debug `forced` calibration mode bypasses the cap AND the adaptive ladder (`AdaptiveQualityManager.kt:59,167,208,298`). If that mode ships enabled, an operator silently floods the uplink at a fixed bitrate, the backlog explodes, and chunks die at TTL — a data-loss footgun."* — **Rebuttal, with the closed footgun cited.** Project memory records this exact footgun (§8.2.8 / commit `2b48610`): the entire DEBUG section, including the fixed-bitrate toggle, is now gated behind `BuildConfig.DEBUG` and the runtime `debugRawAllowed` reads `android:debuggable` directly (tamper-resistant vs `BuildConfig`, `CaptureScratchCleaner.kt:41-56`). In a release build `forced` is never set and `getMaxQualityCap` governs (`StreamRecordingService.kt:1067-1071`). So the footgun is closed in release; an auditor should still verify the gate holds.
- **Assumptions & residual.** Rests on upload-time ratio being a faithful proxy for link capacity (it isn't during concurrency-capping — hence the backlog-forced path as a backstop). The cap is read once at recording start (`AdaptiveQualityManager.kt:82-84`) so a mid-session cap change applies to the *next* recording — accepted UX trade.
- **Questions for the future audit.**
  1. Verify the DEBUG/forced section is genuinely R8-stripped in release and that no pref-only path can re-enable fixed-bitrate (the §8.2.8 fix).
  2. The ladder floors at SD (480p, `StreamQuality.kt:50-54`). On a link too slow even for SD, the backlog grows unbounded → TTL loss. Is there a "pause capture / drop to audio-only" terminal degradation, or does the witness just lose footage?

### 2.8 Data-loss trio — idempotent report index

- **What it is.** `allocateReportIndexForSession` atomically assigns each session a derivation index `n`, idempotent on `sessionId`, counter-committed-before-mapping with `.commit()` (sync) (`StreamPreferences.kt:432-449,510-530`).
- **Affirmative case.** This structurally kills the "split-session" data-loss class (2026-05-20 field bug: a session POSTing report-creation twice → chunks halved across two `report_id`s). A session now has exactly one derived `report_id` fixed *before* the first chunk is enqueued (`StreamRecordingService.kt:690-698,2306-2318`). A process restart mid-session re-derives the same `n` (idempotent), never a second report.
- **Why this implementation.** Counter-first-then-mapping (`StreamPreferences.kt:443-446`) means a crash between the two only *skips* an index (rescue tolerates gaps) and never *reuses* one for two sessions. `.commit()` (not `.apply()`) guarantees durability before return so a kill right after can't lose the mapping or the bumped retry counter (`StreamPreferences.kt:522-529`). The report directory (`report.rs:266-350`) records each allocated index so rescue enumerates `0..n_max` exactly rather than guessing with a hole-tolerance constant.
- **Adversarial stress.** *"`allocateReportIndexForSession` holds a lock and does a synchronous `.commit()` on the init thread — and the rescue path (`OrphanSweepWorker`) calls the *same* allocator concurrently with different unique-work names. Two concurrent allocations for the same offline-start session = a split report on the rescue side."* — **Rebuttal.** The allocator is idempotent under `sessionReportsLock` (`StreamPreferences.kt:437-439`: returns the existing entry if present), and the sweep additionally serializes its whole body under a process-wide `sweepLock` (`OrphanSweepWorker.kt:147-159,447-454`) precisely so periodic-vs-one-shot runs can't each mint a report for the same session. The split class is closed on both the live and rescue sides.
- **Assumptions & residual.** Rests on `SharedPreferences.commit()` being genuinely durable and on `sessionId` being collision-free (it's an opaque token with no internal `_`, `OrphanSweepWorker.kt:398-406`). Does NOT defend a legacy pre-cutover session (server-assigned `reportId`, index -1) — those are skipped and wiped by the clean-break cutover (`OrphanSweepWorker.kt:252-258`).
- **Questions for the future audit.**
  1. The monotone counter is a single `SharedPreferences` int; if the prefs file is corrupted/reset, the counter restarts at 0 and a new session could reuse an index whose old report still exists on the relay. The relay is write-once on differing bytes — does a same-index different-bytes collision fail safe (4xx) or silently corrupt?

### 2.9 Data-loss trio — zombie/orphan sweep with bounded give-up

- **What it is.** A periodic (30 min) + one-shot + network-triggered worker that re-uploads `.strm` blobs left by a stopped session, allocating a rescue index for unmapped offline-start sessions, with a 3-retry give-up budget after which it secure-deletes (`OrphanSweepWorker.kt:84-333`).
- **Affirmative case.** When the user stops with a backlog, those blobs carry the originating session's id and the live `scheduleUpload` filters by *current* session, so they'd never re-upload — they'd just decay at the 48 h TTL (data the user reasonably expected to send). The sweep is the rescue path. Crucially it's the *only* deletion authority on the rescue side, and only after `MAX_RETRIES` *real* attempts (network-absent/ratchet-locked skips don't burn budget, `OrphanSweepWorker.kt:138-145,300-312`), so a transient outage never drops genuine data.
- **Why this implementation.** One-shot runs (fired on unlock) deliberately do NOT bump the budget (`OrphanSweepWorker.kt:301-307,442-444`) — a few rapid unlocks while a blob uploads would otherwise exhaust the 3-retry budget and secure-delete in-flight data. Give-up is thus driven only by *persistent failure despite connectivity*; prolonged-offline sessions fall to the age-based 48 h backstop instead. The network-return trigger (`OrphanSweepWorker.kt:546-592`) cancels grown backoffs and re-enqueues fresh so a backlog drains as soon as wifi returns, not at the next 30 min tick. The 0-30 s jitter on enqueue (`OrphanSweepWorker.kt:345-374`) avoids slamming the relay in lockstep.
- **Adversarial stress.** *"3 retries is a thin margin. Three consecutive transient-but-connected failures (relay flaky, not down) silently secure-delete genuine evidence — and the give-up deletion is unrecoverable."* — **Partial concession, with the mitigations.** The give-up counts ACTUAL deletions, not `orphans.size`, so a blob surviving a failed delete isn't phantom-reported (`OrphanSweepWorker.kt:272-294`), and the loss is surfaced in-app via `addOrphanDeletion(... "unrecoverable")` (`OrphanSweepWorker.kt:292-294`) so it's never *silent*. But yes: a relay that returns a connected-failure exactly 3 times will trigger give-up. The design judgment is that 3 *real* attempts across ≥90 min of periodic ticks (give-up only on the periodic path) is a strong signal of unrecoverability, and the user is told. An auditor may reasonably argue MAX_RETRIES=3 is too aggressive for irreplaceable testimony.
- **Assumptions & residual.** Rests on the in-app banner actually being seen (read after unlock, `StreamPreferences.kt:556-558`). Does NOT retain blobs past 48 h regardless of retry count (the TTL is the hard ceiling, `OrphanSweepWorker.kt:422-432`).
- **Questions for the future audit.**
  1. Is MAX_RETRIES=3 + the 48 h TTL the right risk posture for irreplaceable evidence? A coercion scenario wants fast deletion; a "I lost my only copy of a war-crime recording" scenario wants near-infinite retention. These conflict — which user wins, and is it configurable?
  2. The give-up path is the rescue side's *only* delete authority; confirm no race where the live `sweepStaleChunks` (TTL) and a give-up both count the same deleted blob, double-reporting the loss.

### 2.10 Data-loss trio — dedup via `enqueueUniqueWork(blob.name, KEEP)`

- **What it is.** Both the live path and the sweep enqueue per-blob unique work keyed by filename with `ExistingWorkPolicy.KEEP` (`StreamRecordingService.kt:2254-2259`, `OrphanSweepWorker.kt:383-387`), plus an in-memory `enqueuedBlobNames` set to skip the IPC entirely (`StreamRecordingService.kt:282,2197`).
- **Affirmative case.** Without it, every `scheduleUpload` re-enqueued a worker for every pending blob, so worker count grew **O(N²)** in chunks-during-outage — a real field incident (2 min wifi off → ~24 pending → 301 ENQUEUED workers, `StreamRecordingService.kt:2242-2253`). Dedup keeps one worker per blob, which both prevents duplicate PUTs and keeps the device from thrashing WorkManager's DB.
- **Why this implementation.** Unique-name *per blob* (not per session) keeps independent chunks parallelisable up to the concurrency cap while still deduping each one. KEEP (not REPLACE) preserves a RUNNING worker mid-PUT instead of killing and restarting it. The `enqueuedBlobNames` set is reset on network recovery so FAILED workers can be re-enqueued (`StreamRecordingService.kt:271-283`).
- **Adversarial stress.** *"`enqueuedBlobNames` is process-local and grows unbounded across a long session; and the session-start WorkManager cleanup cancels ENQUEUED workers (`StreamRecordingService.kt:743-767`) — a race could cancel a chunk's only worker right as it's needed."* — **Rebuttal.** The session-start cleanup is carefully scoped (Phase 3.36): it cancels only ENQUEUED `stream_chunk_upload` workers that are NOT orphan-sweep tagged, explicitly preserving RUNNING workers and orphan-sweep work (`StreamRecordingService.kt:749-759`), precisely because earlier blanket `cancelAllWorkByTag` was killing mid-PUT workers and costing data. The set growth is bounded by the session length and dies with the process.
- **Assumptions & residual.** Rests on filenames being globally unique (`<sessionId>_NNNNNN.strm` — unique per session, and session ids don't collide). Does NOT dedup across *different* report indices for the same bytes (not needed — a blob belongs to one session/index).
- **Questions for the future audit.**
  1. The cancelled ENQUEUED workers at session start are re-covered by the orphan sweep for the *previous* session — confirm there's no window where a previous session's last chunk is cancelled but not yet swept, then lost at TTL.

### 2.11 no_auth_token fix — defer JWT auto-clear while encryptions in flight

- **What it is.** The lock-timeout JWT auto-clear (and the ratchet wipe) defer while `encryptionsInFlight() > 0` or the queue is non-empty or the service is running/shutting-down (`V2LockTimeoutController.kt:152-155,217-221`).
- **Affirmative case.** This fixes a 39% data-loss field incident (report `e0201e07`, `V2LockTimeoutController.kt:123-130`): screen off mid-recording → lock-timeout fired while the queue was momentarily empty → JWT wiped → the service produced ~318 more chunks that all looped on `no_auth_token` and died at session end, because the recording service has no re-auth path once the holder is cleared from under it. A chunk mid-encryption is not yet in the queue, so the queue-pending guard alone misses it — the `encryptionsInFlight` counter (`StreamRecordingService.kt:147-160`) closes exactly that gap.
- **Why this implementation.** The counter is incremented *before* the encryption thread starts (`onChunkReady`, `StreamRecordingService.kt:1623-1624`) and decremented in `finally` (`StreamRecordingService.kt:1668-1670`) so no chunk is ever invisible. The whole teardown window is covered by `isRunning || isShuttingDown` (Blue HIGH-6, `StreamRecordingService.kt:111-145,2327-2358`), and workers gate on the same pair (`ChunkUploadWorker.kt:359-371`, `OrphanSweepWorker.kt:100-115`) so a worker can't re-auth against a torn-down ratchet and race the service for an ephemeral slot.
- **Adversarial stress.** *"Deferring the JWT/ratchet wipe while chunks are in flight directly undercuts the auto-lock security control — a coerced witness expects the ratchet to wipe at the timeout; instead it stays unlocked as long as the pipeline is busy, which an adversary could keep busy."* — **Honest tension, conceded as a deliberate trade.** This is a genuine security-vs-resilience conflict. The resolution favors not-losing-the-witness's-words: project memory documents that auto-lock NEVER fires during an active recording (defers if `isRunning`) and re-PINs at return. The wipe is deferred, not cancelled — it fires once the pipeline drains. The residual is a bounded window where a busy pipeline keeps the ratchet warm; an auditor should bound that window and confirm an *explicit* panic-wipe still preempts it unconditionally.
- **Assumptions & residual.** Rests on the in-flight counter being perfectly balanced (every increment has a `finally` decrement) — a leaked increment would defer the wipe forever. `onStartCommand` resets it to 0 defensively (`StreamRecordingService.kt:588-590`). Does NOT defer an explicit `lock()`/`panicWipe()` (those are unconditional per project memory).
- **Questions for the future audit.**
  1. Can a stuck/crashed encryption thread leak the in-flight counter and permanently defer the auto-lock wipe? (The `onStartCommand` reset only helps on the *next* start, not within a wedged session.)
  2. Bound the worst-case "ratchet stays unlocked because pipeline is busy" window and confirm explicit panic-wipe ignores all three deferral guards.

### 2.12 Secure-delete — single-pass overwrite, honest about FBE being the real defense

- **What it is.** `secure_delete_file` opens write, overwrites with `OsRng` bytes, `sync_all`, truncates to 0, unlinks — single pass (`secure_delete.rs:65-100`). Used everywhere a secret file is removed (plaintext MP4, `.strm` blobs, debug dirs).
- **Affirmative case.** It's the right *defense-in-depth* primitive: `unlink(2)` alone leaves data in the freelist recoverable by photorec/TestDisk on a key-compromised device (`secure_delete.rs:6-11`). The overwrite + fsync forces the random bytes out of page cache to disk before unlink, shrinking that recoverable set. Single-pass is correct on NAND (NIST SP 800-88 "Clear"; multi-pass Gutmann/DoD are magnetic-era myths, `secure_delete.rs:42-48`). `OsRng` via syscall is a side-effect neither LLVM nor JIT can elide (`secure_delete.rs:82-84`) — a subtle but important anti-DSE property.
- **Why this implementation.** Rust, not Kotlin `File.delete()`, so the overwrite is a real syscall sequence; every callsite wraps it with a `File.delete()` fallback so a secure-delete failure never leaves the file (`StreamChunkEncryptor.kt:77-94`, `ChunkUploadQueue.kt:156-162`). Idempotent on a missing file so callers needn't pre-check (`secure_delete.rs:61-68`).
- **Adversarial stress.** *"On a wear-levelled/log-structured flash, your overwrite lands in fresh cells and the original ciphertext sectors persist. `set_len(0)` + unlink rely on the controller's TRIM, which is implementation-dependent. So secure-delete is essentially theatre against forensics."* — **Conceded, explicitly, in the source.** The module header states exactly this (`secure_delete.rs:24-40`) and names **FBE as the real line of defense**: against an adversary without the device key, the residue is ciphertext, full stop. Secure-delete is *only* meaningful in the key-compromised / live-RAM branch, where it's a probabilistic improvement, not a guarantee. This is the honest posture an auditor wants — the code doesn't oversell.
- **Assumptions & residual.** Rests on FBE being active and the device key not being held by the adversary for the in-scope threat (locked-device seizure). Does NOT claim cryptographic erasure of the underlying flash cells. The real "erase everything instantly" primitive is FBE key destruction (panic-wipe), not this.
- **Questions for the future audit.**
  1. Does `strmEncryptFile` (the encryptor's Rust write) `sync_all` its output before the plaintext is secure-deleted? If not, a crash leaves a partial `.strm` and a deleted plaintext (see 2.2 Q1) — secure-delete's durability is moot if the *replacement* isn't durable.
  2. On the device matrix, is FBE confirmed active (not just FDE/legacy) so the "ciphertext residue" claim actually holds? This is the load-bearing assumption under the entire secure-delete concession.

## 3. Domain coherence & tensions

The domain hangs together around one invariant: **a chunk, once captured, is either uploaded or explicitly destroyed-and-surfaced — never silently lost.** Every failure path chooses `retry` over `failure` (transport, 425, 429, 507, native-throw); the only deletion authorities are (a) success-after-upload, (b) the 48 h TTL, and (c) the rescue give-up after 3 real attempts — and (b)/(c) both write an in-app loss event. Idempotency (2.3) is what makes "retry liberally" safe; the per-session index (2.8) is what makes idempotency *correct* (no split). The circuit breaker (2.4/2.5) and concurrency cap (2.6) protect the shared relay and the scarce auth-slot budget so the liberal-retry posture doesn't become a self-DoS. The adaptive quality ladder (2.7) keeps capture and upload in balance so the backlog doesn't outrun the TTL.

Three internal tensions deserve the next audit's attention:

1. **Resilience vs the security controls.** The no_auth_token fix (2.11) and the auto-lock-defers-during-recording rule deliberately *delay* the ratchet/JWT wipe to avoid stranding the last (often most critical) chunk. That is a conscious "don't lose the witness's words" choice that softens the auto-lock guarantee. The two are reconciled only by the claim that explicit panic-wipe preempts unconditionally — which must be verified, not assumed.

2. **Relay-not-vault vs retry-forever.** 507/transport retries keep evidence on-device until it can leave (2.5) — but a hostile or broken relay (or a permanently-broken `.so`, 2.3) turns "relay" back into "vault" for up to 48 h. The TTL + panic-wipe are the pressure-release valves; the residual on-device window under a hostile relay is real and accepted.

3. **Aggressive give-up vs irreplaceable evidence.** MAX_RETRIES=3 (2.9) and the 48 h TTL optimise for a small, bounded seizure surface. For a witness whose phone holds the *only* copy of irreplaceable footage, that same aggression is a data-loss risk. The trade is currently fixed, not user-tunable.

A coherence strength worth noting: nearly every constant and code path here is annotated with the dated field incident that produced it (O(N²) workers, the 57 s starvation, the 39% no_auth_token loss, the 55 s quality oscillation, the split-report bug). This domain is empirically hardened, not speculatively designed — which is exactly what makes its *remaining* assumptions (FBE active, `.so` healthy, relay honest, panic-wipe unconditional) the highest-value audit targets.

## 4. Top-3 questions this domain hands to the future adversarial audit

1. **Is the encrypted `.strm` durable before its plaintext source is destroyed?** The queue fsyncs the directory rename (2.2) but the load-bearing question is whether `strmEncryptFile` `sync_all`s the *output* `.strm` before `encryptChunk` secure-deletes the plaintext MP4 (`StreamChunkEncryptor.kt:84-95`). If not, a power-loss/crash in that window destroys the only copy of that chunk's data — the one place the "never silently lose a chunk" invariant could break by construction.

2. **Does panic-wipe / explicit lock unconditionally preempt every resilience deferral?** The no_auth_token fix and auto-lock-during-recording defer the ratchet/JWT wipe while the pipeline is busy (2.11). An auditor must confirm — and ideally bound the window for — that an *explicit* panic-wipe ignores `encryptionsInFlight`, `isRunning`, `isShuttingDown`, and queue-pending, so a coerced witness's wipe is never delayed by a busy or wedged pipeline (and that a leaked in-flight counter can't strand auto-lock forever).

3. **Can the client detect a relay that acks-and-drops, or a permanent client-side break, before the 48 h TTL eats the evidence?** Retry-never-fail (2.3/2.5) assumes the relay is honest about 2xx/507 and that a healthy build will eventually run. There is no client-side read-back confirming a chunk was persisted, no covert-mode signal that uploads are stuck (notifications are off, 2.5 Q2), and a permanently-broken `.so` retries into the TTL (2.3). Probe whether evidence can be silently lost despite the device believing it was safely relayed.
