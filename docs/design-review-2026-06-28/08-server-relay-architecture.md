# Server / relay architecture — Design rationale (adversarial steelman)
> Model: claude-opus-4-8[1m]. Date: 2026-06-28. Scope: the Python FastAPI + MinIO + nginx blind relay (`server/app/*`, `server/deploy/*`) — why a thin semi-trusted relay, how it stays blind, and the deployment posture.

## 1. Scope & the choices under review

The relay's whole reason to exist is the motto: *"tout quitte le téléphone & une saisie n'expose rien ; le téléphone est un relais, pas un coffre."* The phone must shed data fast, and neither the phone **nor the server** may expose anything on seizure. The server choices that implement this:

- **Thin semi-trusted relay (verify-then-store) rather than a trusted backend or P2P** — the app is named "STREAM Blind Relay" / "Zero-knowledge relay server for STREAM encrypted blobs" (`server/app/main.py:67-71`). It verifies signatures, enforces anti-replay, stores opaque bytes, never decrypts.
- **Capability-addressed, identity-free reports** — `report_id = SHA-256("stream.report.id.v1" || report_pk)[..16]` (`server/app/routes/upload.py:20-24`); the only at-rest record is `report_id -> report_pk` with deliberately no owner/author/createdAt/title (`server/app/routes/reports.py:24-31`).
- **Per-chunk capability signatures (domains 0x07/0x08), JWT used once then discarded** (`server/app/routes/upload.py:73-170`, `server/app/signature_domain.py:36-37`).
- **Ephemeral-ratchet auth (V2): enroll / verify / rotate-batch, no persistent bearer** (`server/app/routes/auth_v2.py`, `server/app/ratchet_registry.py`).
- **JWT HS256 single-secret, no refresh token, env-mandated secret, blacklist revocation** (`server/app/config.py:13-37`, `server/app/auth.py:207-258`, `server/app/jwt_blacklist.py`).
- **Nonce-based anti-replay, persisted, clock-skew-bounded, signed-timestamp-pinned** (`server/app/auth.py:122-204`).
- **Write-once immutable blobs + check-then-commit creation budget** (`server/app/storage.py:192-225`, `server/app/ratchet_registry.py:247-313`, `server/app/routes/upload.py:155-247`).
- **MinIO loopback bind + internal docker bridge, no public S3 surface** (`server/docker-compose.yml:31-38`, `server/app/config.py:7-11`).
- **Bounded, IP-scrubbed, traceback-scrubbed JSON logging** (`server/app/logging_setup.py`, `server/deploy/nginx/relay.conf.template:63-64`, `server/Dockerfile:50-52`).
- **Hardened container + single-worker invariant** (`server/Dockerfile:1-81`, `server/docker-compose.yml:97-128`).
- **Deployment posture: disposable test server, single DOMAIN flag, destructive prod cutover that wipes state** (`server/deploy/README.md`, `server/deploy/nginx/render-relay-conf.sh`).
- **Long blob TTL justified by E2E encryption; periodic blob + report GC** (`server/app/config.py:56-69`, `server/app/blob_cleanup.py`, `server/app/report_cleanup.py`).

## 2. Choice-by-choice rationale

### 2.1 A thin semi-trusted relay, not a trusted backend and not P2P

- **What it is** (`server/app/main.py:67-71`, `server/app/routes/archive.py:1-24`). The server is a "blind relay": it authenticates writers cryptographically, stores E2E-encrypted STRM blobs as opaque bytes, and serves them back to anyone who presents the 128-bit `report_id` capability. It never holds a decryption key and the comment block in `archive.py:6-11` states plainly: "The relay never learns which identity reads which reports … the server is blind."

- **Affirmative case.** The motto demands two things that pull in opposite directions: data must *leave the phone fast* (so it survives device seizure), yet *a seizure of wherever it lands must expose nothing*. A blind relay squares this circle. Speed: the phone uploads chunks the moment they seal and can wipe them (the relay is the drain, not a vault on the phone). Seizure-resistance: because the relay only ever holds ciphertext keyed to phrase-derived secrets that never leave the client, a server seizure yields bytes that are "inexploitables sans les clés client" (`server/app/blob_cleanup.py:20-23`). The relay is *semi*-trusted, not trusted: it is trusted only for **availability and anti-abuse**, never for **confidentiality or identity**.

- **Why this implementation (alternatives rejected).**
  - *Trusted backend (server holds keys / decrypts / maps users→content).* Rejected outright: it makes the server a coffre — the exact thing the motto forbids. One subpoena or seizure would expose every witness's footage and their identity↔activity graph. The whole architecture is built to ensure the operator *cannot* comply even under coercion.
  - *Pure P2P / no server.* Rejected on field-reality grounds. The threat model is activists on intermittent mobile networks who need footage off the device *immediately* and durably, even when the witness's own device is then seized or dies. P2P requires a peer to be online and reachable; it offers no durable, always-available drain. A relay also lets the device be wiped without losing the rushes. The config comments repeatedly cite intermittent field connectivity (`config.py:56-69`, "réseau intermittent en déplacement") as the binding constraint — P2P would make that worse.
  - *A "dumb" pure object store (e.g. raw S3 bucket, no app server).* Rejected because a pure store cannot enforce anti-replay, anti-sybil, the write-once immutability gate, or scrubbed logging. The thin FastAPI layer exists precisely to add *only* those semi-trust functions on top of MinIO, and nothing more.

- **Adversarial stress.** *"Semi-trusted still means trusted for metadata — the relay sees source IPs, timing, sizes, and upload cadence even if it can't read content. A seizure of a live relay or a wiretap upstream reconstructs who-filmed-what-when without ever breaking the crypto."* **Partial concession.** This is the real residual and the design knows it: IP is scrubbed from app logs (`logging_setup.py:46-60`), nginx access logs are off (`relay.conf.template:63-64`), and the README even disables the *global* nginx access log (`deploy/README.md:131-147`). But scrubbing logs does not stop a network-position adversary (the state, by assumption) from observing TLS flows to the relay IP, and the relay process *does* transiently see `request.client.host` (it must, for per-IP rate limiting via `--forwarded-allow-ips`, `Dockerfile:65-77`). The mitigations narrow the *at-rest* footprint to near zero; they do not defeat *on-path* traffic analysis. That is delegated to the transport layer (ObfQuic / domain fronting — out of this domain's scope) and is the single biggest thing this domain hands upward.

- **Assumptions & residual.** Rests on: (a) the client-side E2E crypto being sound (out of scope here, audited elsewhere); (b) the operator being honest-but-coercible (the design protects against a *compelled* operator by ensuring there is nothing to compel — no keys, no identity map); (c) TLS + SPKI pinning protecting the channel. It does **not** claim to hide that *a* relay exists or that *traffic* flows to it.

- **Questions for the future audit.** (1) Is "the operator literally cannot decrypt" actually true end-to-end, or is there any code path (debug, OTS, error handling) where plaintext or a key transits the server? (2) What is the metadata exposure of a *malicious* relay operator who logs at the TLS/socket layer below the app — is the threat model's "honest-but-coercible" assumption defensible, or should the design assume a fully hostile relay?

### 2.2 Capability-addressed, identity-free reports

- **What it is** (`server/app/routes/upload.py:20-24`, `server/app/routes/reports.py:24-31`, `server/app/routes/archive.py`). A report's address is `report_id = SHA-256(ctx || report_pk)[..16]` — a 128-bit value derived from a per-report public key, which is itself derived from the BIP-39 seed. The only persisted record is `{report_id, report_pk}` (`reports.py:106`). There is "deliberately NO owner, NO author, NO createdAt, NO title" (`reports.py:24-26`). Archive reads need no token at all: knowing the 128-bit `report_id` *is* the read capability (`archive.py:13`, `upload.py:62-65`).

- **Affirmative case.** This is the at-rest embodiment of "une saisie n'expose rien." Seize the relay's disk and you get a list of opaque 16-byte ids each bound to a 32-byte public key, plus ciphertext blobs. There is no join from any of that to a human, to a device, or to "which person uploaded this." The README's post-cutover acceptance test literally greps the state for `owner|createdAt|author|title` and asserts zero matches (`deploy/README.md:399-401`). Capability addressing also gives the rescue flow its elegance: a re-installed device re-derives `report_id_0, 1, 2…` from the phrase and enumerates its own archive with *no* server-side "list my reports" call (`archive.py:5-8`) — so the server never even learns the *set* of reports one identity owns.

- **Why this implementation (alternatives rejected).**
  - *Owner-keyed reports (`report -> user_id`).* This was the *old* schema; Phase C deliberately broke it (`deploy/README.md:331-334`: "L'ancien état (owner-based) est incompatible … d'où le clean break"). Owner-keying creates exactly the identity↔activity join the motto forbids.
  - *Token-gated archive reads (an archive-scope JWT).* Existed and was *removed* (`auth.py:216-223`, `_deps.py:48-50`, `archive.py:20-24`): an archive token would make the relay learn "which identity reads which reports." Capability addressing (the unguessable 128-bit id) replaces authentication with possession, which leaks no identity.
  - *Random server-assigned report ids.* Rejected because then the rescue device couldn't *re-derive* its ids from the phrase alone — it would need a server-side index keyed by identity, reintroducing the join. Deriving the id from the report key makes the address self-authenticating and client-recomputable.

- **Adversarial stress.** *"`report_pk` is stored in cleartext and `report_id = H(report_pk)`. If the same master seed derives all of a witness's `report_pk`s, an adversary who compromises the seed (or the derivation) can enumerate every report; and even without the seed, the set of `report_pk`s in `reports.json` is a fingerprint — are they linkable to each other or to an identity?"* **Rebuttal with conceded edge.** The per-report keys are described as "unlinkable to the identity or to other reports without the witness's secret master" (`reports.py:27-29`). So linkage requires the master secret, which never touches the server — consistent with the motto. The honest residual: this *assumes* the client-side derivation is hardened (domain-separated, not trivially enumerable from one leaked `report_pk`). That is a crypto-domain claim the server takes on faith; the server audit should flag it as a cross-domain dependency. Second honest concession already in the code: `report_id`'s 128-bit space makes it unguessable, but `last_modified` on the MinIO object still leaks the *when* of upload (`report_cleanup.py:8-12`, `reports.py:143-147`) — "no extra timestamp kept" is not "the when is sealed."

- **Assumptions & residual.** Rests on: 128 bits being enough to make `report_id` unguessable (it is — brute force is infeasible and rate-limited, `upload.py:60`); SHA-256 second-preimage resistance binding id↔key (`upload.py:113-116`); and the client deriving unlinkable per-report keys. Does **not** claim to hide upload timing (object-store `last_modified` leaks it) nor the count/size distribution of blobs.

- **Questions for the future audit.** (1) Given a single leaked `report_pk` from `reports.json`, can an adversary derive or recognize sibling `report_pk`s of the same witness? (verify the unlinkability claim against `crypto-rs/core/src/report.rs`). (2) Is the 128-bit truncation of SHA-256 for `report_id` safe against a *birthday* collision that could let two reports alias (DoS / cross-write), given the write path keys storage by `report_id`?

### 2.3 Per-chunk capability signatures; JWT used once then discarded

- **What it is** (`server/app/routes/upload.py:73-247`). Every PUT carries `X-Report-PK` + `X-Report-Write-Sig` (the per-report key `R_n` signs `0x08 || report_id || filename || sha256(body)`). Only the *creating* chunk also carries a stream JWT + `X-Report-Create-Sig` (`0x07 || report_id || report_pk`). The JWT's subject is used exactly once for the anti-abuse counter and then `del payload` / discarded (`upload.py:148-170`) — never written with the report.

- **Affirmative case.** This is "the phone is a relay, not a vault" applied to write authorization: the authority to write a chunk is a *per-report* capability, not the witness's identity. Even the one place identity appears (the enrollment JWT proving anti-sybil standing) is consumed transiently and never persisted (`upload.py:160-170`, "lives in RAM for the request and is never written to disk — relay-blind-at-rest is unchanged"). The write signature covers the body hash *that storage actually persists* (`upload.py:193-201`), so a man-in-the-middle or a malformed proxy cannot substitute bytes without invalidating the signature. The ordering is carefully chosen (id↔pk binding first, cheap header checks before the expensive body stream, blob durable before any record) so the invariant "a record implies ≥1 durable blob" holds (`upload.py:94-103`).

- **Why this implementation (alternatives rejected).**
  - *Bearer-JWT-only writes (the V1 path).* Removed (`auth_routes.py:14-25`): a long-term Ed25519 signature minting a scopeless upload JWT was "a non-ratchet creation path that contradicts decision 'creation is ratchet-gated'." A persistent bearer that authorizes arbitrary writes is exactly the seizable credential the design eliminates.
  - *Identity-signed chunks.* Rejected: it would write the identity (or a stable per-identity signature) alongside every blob, reintroducing the at-rest join. Per-report `R_n` keys keep each report's write-authority self-contained and identity-free.
  - *No per-chunk signature (trust the JWT for all chunks).* Rejected because the §10.6 finding (`storage.py:22-34`) showed a leaked 24h JWT surviving in the JVM heap could corrupt already-stored chunks; per-chunk write-sigs + write-once close that.

- **Adversarial stress.** *"The create path still requires a JWT, and that JWT *is* identity-bound (subject = `ed25519_pk`). For the duration of the request the relay holds the identity in RAM and increments a per-identity counter on disk. A memory-scraping adversary on the live host, or anyone reading `.ratchet_registry.json`, sees per-identity batch/creation counts — a gross activity curve."* **Honest concession, bounded.** The code concedes precisely this: the counter is "a count per `batch_number` (numbers, gross activity), never a report↔identity map — same residual class as `consumed_indices`" (`ratchet_registry.py:265-268`), and the rotation deliberately *drops* the previous batch's counters so the at-rest curve doesn't accumulate history (`ratchet_registry.py:232-238`). So the residual is "the *current* batch's gross creation count per enrolled identity," not "which reports, when, or a longitudinal history." This is a defensible trade: anti-sybil needs *some* per-identity bound, and this is the minimum that buys it. The future audit should still weigh whether even a current-batch count is more than the motto can bear.

- **Assumptions & residual.** Rests on Ed25519 signature soundness, on `report_id == H(report_pk)` being enforced before any storage (it is, `upload.py:113-116`), and on the body hash used for the write-sig being byte-identical to what MinIO stores (it is — same `hasher` object, `upload.py:178-209`). Does **not** claim the create-path is fully identity-free (it isn't — a transient, current-batch, count-only residual remains by design).

- **Questions for the future audit.** (1) Can a subsequent (non-creating) chunk ever create or resurrect a report without the JWT gate — i.e. is the `is_creation` branch (`upload.py:119-133`) truly the only write-without-JWT path, and is the 425 "retry" response safe against an attacker racing a creating PUT? (2) The per-identity creation counter is the only at-rest identity residual on the write path — is it strictly necessary, and could it be replaced by a per-batch (not per-identity) anonymous token?

### 2.4 Ephemeral-ratchet auth (V2): no persistent bearer

- **What it is** (`server/app/routes/auth_v2.py`, `server/app/ratchet_registry.py`). An identity enrolls a batch of 50 ephemeral public keys signed by its long-term key (`enroll`, domain 0x03). To authenticate it signs a server nonce with one *ephemeral slot* key (`verify`, domain 0x01), and that slot is consumed (`consume_ephemeral_key`, `ratchet_registry.py:165-190`) — single-use, forward-secure. Rotation (domain 0x02) advances to a fresh batch, the previous signer authenticating the new batch (`rotate_batch`, `ratchet_registry.py:193-244`).

- **Affirmative case.** Each authentication burns a one-time slot, so a captured auth artifact cannot be replayed and a stolen long-term key cannot mint unlimited future logins without re-enrolling. This is the auth-layer expression of forward secrecy: compromise *now* does not retroactively unlock past sessions, and the persistent credential surface is minimized. The design explicitly frames "refresh" as "a new `/auth/v2/verify` with the next slot" (`config.py:20-37`) rather than a long-lived refresh token — a refresh token "would reintroduce exactly the persistent bearer the ephemeral ratchet exists to eliminate." That is the motto applied to credentials.

- **Why this implementation (alternatives rejected).**
  - *Classic username/password + long-lived session.* Entirely removed (`config.py:78-82`, `auth.py:292`). A reusable credential is a seizable credential.
  - *Refresh tokens.* Rejected by design (`config.py:20-26`) for the reason above.
  - *Stateless auth with no consumption tracking.* Rejected — without the consumed-index set the server can't enforce single-use, so a captured signature would replay. The registry's `consumed_indices` (`ratchet_registry.py:48-49`) is the minimal state that makes slots one-time.

- **Adversarial stress.** *"The registry stores, per identity at rest: long-term `ed25519_pk`, the current batch's 50 keys, consumed indices, enrolled_at/updated_at timestamps, and creation counts (`ratchet_registry.py:116-125`). That is a per-identity activity ledger with timestamps — a seizure of `.ratchet_registry.json` shows who is enrolled and roughly how active they are."* **Concession, with the timestamps as the sharpest point.** `enrolled_at` and `updated_at` are *absolute timestamps per identity* (`ratchet_registry.py:122-124, 188, 240, 284, 311`). Unlike the report path (which dropped `createdAt`), the auth registry keeps a per-identity "first seen / last active" pair. The design accepts the registry as a "résidu §6" (a known residual, `deploy/README.md:434-435`) — the auth layer *needs* per-identity state to prevent replay and sybil, so it cannot be fully identity-free the way reports are. The honest gap: the *timestamps* are arguably more than replay/sybil prevention strictly requires (consumed-index sets and counts would suffice without absolute wallclock). A future hardening could coarsen or drop them.

- **Assumptions & residual.** Rests on the long-term key being held only on-device, on Ed25519 soundness, and on the registry surviving restarts (atomic JSON persist, `ratchet_registry.py:56-74`). The auth registry is the **one place the relay is *not* identity-free** — and the design says so explicitly. It does not claim otherwise.

- **Questions for the future audit.** (1) Are `enrolled_at`/`updated_at` necessary, or can they be dropped/coarsened to shrink the at-rest activity ledger? (2) On seizure of `.ratchet_registry.json` + `reports.json` together, is there *any* correlation (timing, ordering, count) that re-joins an identity to its reports despite the report side being identity-free?

### 2.5 JWT HS256, single shared secret, no refresh, env-mandated, revocable

- **What it is** (`server/app/config.py:13-37`, `server/app/auth.py:207-258`, `server/app/jwt_blacklist.py`). After a successful ephemeral verify, the relay issues an HS256 JWT signed with a single server-side `JWT_SECRET` that **must** come from env (the process `sys.exit(1)`s if it is missing, `config.py:14-17`). Default lifetime 24h, env-tunable. Revocation is a SHA-256-keyed blacklist checked before signature verification (`auth.py:251-256`, `jwt_blacklist.py`).

- **Affirmative case.** HS256 with one secret is the *right* simplicity here, not a corner cut: the relay is **both the issuer and the only verifier** of these tokens. Asymmetric JWT (RS256/ES256) exists to let *third parties* verify without holding the signing key — there is no third party in this architecture, so RS256 would add key-management surface for zero benefit. A single secret is therefore the minimal, auditable choice. Mandating it from env (no auto-generation, `config.py:13`) prevents the classic footgun of a dev default secret silently shipping to prod. The "no refresh token" stance (2.4) keeps the JWT a short, RAM-only (`config.py:31-32`) credential whose theft is bounded by `exp` *and* killable immediately via `/logout` (`auth_v2.py:389-439`).

- **Why this implementation (alternatives rejected).**
  - *RS256/ES256 (asymmetric).* Rejected: no external verifier exists; it only adds a private-key-management problem.
  - *Auto-generated secret.* Rejected (`config.py:13`, "no auto-generation"): an auto-secret either resets on restart (invalidating all tokens) or gets persisted insecurely.
  - *Redis-backed revocation.* Deferred (`jwt_blacklist.py:18-20`): single-worker (2.10) makes a process-local dict sufficient; Redis is a follow-up. Storing the *hash* not the token (`jwt_blacklist.py:14-17`) keeps the blacklist compact.
  - *No revocation (rely on `exp`).* Rejected because a lost device's 24h token would stay live; `/logout` lets another device kill it now.

- **Adversarial stress.** *"A single HS256 secret is a single point of catastrophic failure: leak `JWT_SECRET` (env dump, backup, `.env` in a tarball) and an attacker forges arbitrary tokens for any identity. And HS256 is the home of the classic `alg:none` / RS-vs-HS confusion bugs."* **Rebuttal.** The `alg` confusion class is closed: the relay pins `algorithms=[config.JWT_ALGORITHM]` on every decode (`auth.py:256`, `auth_v2.py:418-420`) and `JWT_ALGORITHM` is the constant `"HS256"` (`config.py:19`) — PyJWT will reject `none` and an RS-signed token. The secret-leak risk is real but *bounded by the design's own posture*: a forged JWT only authorizes the *create* path's anti-sybil check — it does **not** decrypt blobs, does not read the archive (archive is token-free capability-addressed, 2.2), and a forged token still cannot produce a valid per-chunk write-sig without the per-report key (2.3). So even a full `JWT_SECRET` compromise lets an attacker *create spam reports up to the budget*, not exfiltrate or corrupt witness footage. The backup-in-tarball angle is the residual worth flagging (the backup scripts dump the volumes; `.env` is host-path, not in the volume — `deploy/README.md:327-329` notes TLS is host-path, and `.env` lives in `/opt/frappuccino/.env`, *outside* `server_state`, so it is not in the state tarball — good, but worth verifying).

- **Assumptions & residual.** Rests on `JWT_SECRET` being high-entropy (the example uses `openssl rand -base64 48`, `.env.example:5`) and kept out of git (`.env` gitignored, `deploy/README.md:442-444`). Does not claim a leaked secret is harmless — it claims the blast radius is "spam reports," not "broken confidentiality."

- **Questions for the future audit.** (1) Confirm the blast radius claim: is there *any* endpoint where a forged stream JWT (no per-report key) achieves more than budget-bounded report creation? (2) Is `JWT_SECRET` reliably excluded from the backup tarballs and off-host copies (`backup-state.sh`), or can a stolen backup yield the forging secret?

### 2.6 Nonce anti-replay: persisted, signed-timestamp-pinned, skew-bounded

- **What it is** (`server/app/auth.py:122-204`). `/auth/challenge` mints a 32-byte nonce + a server timestamp, persisted atomically to disk. The client must sign `domain || nonce || ts_be_u64`. Verify pops the nonce atomically (single-use), rejects if the client-echoed timestamp ≠ the stored one, and rejects if `|now - ts| > 30s` (`auth.py:178-187`, `CHALLENGE_CLOCK_SKEW_TOLERANCE_SECONDS = 30`, `NONCE_TTL = 60`).

- **Affirmative case.** This stops replay of a captured auth exchange — the core anti-impersonation guarantee. Persisting the cache (`auth.py:16-28`) closes a subtle hole: an in-memory-only cache would, on restart, "re-open a 60s replay window on all captured nonces" (`auth.py:58-64`, `atomic_io.py:1-26`). Pinning the timestamp to the *server-minted* value and refusing the client's version if it diverges (`auth.py:182-185`) prevents a client from stretching the validity window. The skew tolerance is sized to "NTP drift + Android sleep + network latency" without exceeding the nonce TTL (`auth.py:113-116`).

- **Why this implementation (alternatives rejected).**
  - *In-memory-only nonce cache.* Rejected — restart replay window (above).
  - *Trust the client's timestamp.* Rejected — a client could backdate to widen replay; the server stores its own `ts` and compares (`auth.py:181-185`).
  - *No skew tolerance (exact match).* Rejected — clock drift on field Android devices would reject legitimate auths; 30s is the calibrated middle.

- **Adversarial stress.** *"The nonce cache is process-local in one worker; the persistence + the rollback-on-OSError dance (`auth.py:135-142`, `167-177`) is intricate — a bug there could either lose nonces (DoS) or double-accept (replay). And under flood the cache could bloat."* **Rebuttal.** The flood-bloat concern was found and fixed (R-MED-3): a background `nonce_cleanup_loop` purges expired nonces every 60s regardless of request load (`auth.py:303-359`, `main.py:43-49`), keeping the cache bounded independent of the O(N)-per-insert path. The rollback paths are explicitly designed to keep in-memory and on-disk consistent (pop-and-restore on save failure → 503 → client retry), so the failure mode is "retry," not "replay." Replay safety depends on the single-worker invariant (2.10) — with multiple workers each cache is independent and a nonce minted by worker A is unknown to worker B, which is why `--workers 1` is load-bearing and enforced (`Dockerfile:42-48`).

- **Assumptions & residual.** Rests hard on single-worker (replay safety is *not* preserved under multi-worker). Rests on the disk surviving (atomic write + fsync, `atomic_io.py:79-88`). Does not claim multi-worker safety — the codebase forbids multi-worker precisely because of this.

- **Questions for the future audit.** (1) Trace every persistence-failure path in nonce mint/verify (`auth.py`, `auth_v2.py:52-71`) for a window where a nonce is accepted in-memory but a concurrent reader could re-pop it. (2) Is 30s skew + 60s TTL a safe combination against a fast on-path replayer within that window, given the relay's RTT?

### 2.7 Write-once immutable blobs + check-then-commit creation budget

- **What it is** (`server/app/storage.py:158-225`, `server/app/ratchet_registry.py:247-313`, `server/app/routes/upload.py:155-247`). A PUT to an occupied key is allowed only if the incoming SHA-256 matches the stored object (idempotent no-op); different bytes → `WriteOnceConflictError` → HTTP 409. Report creation reserves a budget slot atomically (`reserve_report_creation`) and releases it on any failure before the record is durable (`release_report_creation`, `upload.py:240-247`).

- **Affirmative case.** Write-once defends the integrity of already-captured footage against a *leaked write capability*: even if an attacker obtains a valid upload JWT (the §10.6 heap-survival finding, `storage.py:22-34`), they cannot overwrite a stored witness chunk with garbage — there is no DELETE route and an occupied key is immutable. Idempotent re-PUT of identical bytes is still allowed, so the legitimate retry/race semantics the field workflow relies on (Phase 1.12/3.41) are preserved. The creation budget caps a sybil from minting unbounded reports on one enrolled batch (`config.py:47-54`), and the *atomic reserve* (vs the old peek-then-commit) closes a check-vs-commit TOCTOU under the single async worker (`ratchet_registry.py:247-260`, audit R-SRV-3).

- **Why this implementation (alternatives rejected).**
  - *Idempotent overwrite (the prior Phase 3.12 behaviour).* Rejected after §10.6: overwrite let a leaked token corrupt stored chunks. Write-once is the fix while keeping RFC-9110 PUT idempotence for identical bytes.
  - *Append/resume PUT (download-old + concat + re-put, the original).* Rejected (`storage.py:108-127`): a reconnect race appended bytes to themselves producing 2× blobs that fail to decode. PUT-overwrite-then-write-once is simpler and race-benign.
  - *Hard per-IP/global report cap.* Rejected in favor of per-(identity,batch) so legitimate heavy field use isn't throttled while a single sybil is bounded; the count is the minimal anti-abuse state (2.3).
  - *Multipart upload (length = -1).* Explicitly rejected (`storage.py:144-149`): multipart is not idempotent (orphan parts on disconnect) and would break the PUT-overwrite guarantee.

- **Adversarial stress.** *"Write-once computes the existing object's hash by streaming it back from MinIO on every re-PUT to an occupied key (`storage.py:158-189`). An attacker who knows a `report_id`+filename can force the relay to GET-and-hash a large blob repeatedly — an amplification / I/O-DoS on the single worker."* **Partial rebuttal.** The read-back only happens on a PUT to an *already-occupied* key, and the legitimate client HEADs first and skips stored chunks (`storage.py:163-170`), so the read-back is "the rare path." But the attacker doesn't follow the client's politeness — they *can* force it. The mitigations are: the write-sig must verify *before* the store call (`upload.py:201-209`), so an attacker without the per-report key never reaches `upload_blob_stream_write_once`; and the body must be fully streamed+hashed first anyway (bounded by `MAX_UPLOAD_SIZE`). So the amplification requires a *valid* write-sig (i.e. the per-report key), which an attacker by assumption lacks. Residual: a witness with their own key could self-DoS, which is not in the threat model. Honest note: `/file/{report_id}/{filename}` PUT has **no slowapi rate-limit** (only the HEAD does, `upload.py:59-60`); nginx caps body size/timeout (`relay.conf.template:60-61`) but per-IP PUT-rate bounding is left to nginx/transport, worth confirming.

- **Assumptions & residual.** Rests on the write-sig gate preceding the expensive read-back, on SHA-256 being the integrity oracle (computed from bytes-on-disk, not a trusted ETag — `storage.py:158-170`), and on single-worker serializing the budget reserve. Does not claim PUT is rate-limited at the app layer (it relies on nginx + the write-sig gate).

- **Questions for the future audit.** (1) The unauthenticated-at-app-layer PUT path: confirm nginx (and only nginx) bounds PUT request rate, and that a flood of PUTs with *invalid* write-sigs is cheaply rejected before any MinIO round-trip. (2) Verify the reserve/release budget pairing has no path where a slot is reserved but never released on an exotic exception (the `finally` at `upload.py:240-247` looks complete — stress it).

### 2.8 MinIO loopback bind, no public S3 surface

- **What it is** (`server/docker-compose.yml:31-38`, `server/app/config.py:7-11`). The MinIO S3 API is published only on `127.0.0.1:9000`; the app reaches it over the internal docker bridge (`MINIO_ENDPOINT: minio:9000`) which does not use the published port. The console (9001) is not exposed at all.

- **Affirmative case.** This is straightforward attack-surface minimization with a sharp, documented rationale: a bare `9000:9000` publishes on `0.0.0.0` *and* "Docker's iptables rules bypass UFW, exposing the raw S3 surface to the internet despite `ufw default deny`" (`docker-compose.yml:31-37`). Binding to loopback closes a footgun that the host firewall would *not* have caught — the relay's only public face is nginx:8443, never raw MinIO.

- **Why this implementation (alternatives rejected).**
  - *Publish 9000 on 0.0.0.0 (the naive default).* Rejected — UFW-bypass exposure (above).
  - *Don't publish 9000 at all (bridge-only).* Would be even tighter; loopback is kept presumably for host-side `mc`/debug access. Worth questioning (see below).
  - *Expose the console for ops.* Rejected — not exposed; ops via internal network only (`docker-compose.yml:38`).

- **Adversarial stress.** *"Loopback still means anything on the host (a compromised co-tenant process, an SSRF in another service, the relay process itself post-RCE) can hit the raw S3 API with the root credentials and read/delete every blob."* **Concession.** True — loopback is host-trust, not zero-trust. The mitigations are container hardening (2.10, `cap_drop ALL`, `no-new-privileges`, read-only FS, non-root) and the fact that the blobs are E2E-encrypted (raw S3 access yields ciphertext, consistent with the motto). The residual is *deletion* (availability) rather than *disclosure*: a host attacker could wipe blobs, which the backup posture (2.9) is meant to recover from. Tightening to bridge-only (no loopback publish) would remove even that, at the cost of host-side debuggability.

- **Assumptions & residual.** Rests on host integrity and on E2E encryption making raw blob access non-disclosing. Does not claim defense against a fully host-compromised attacker (that attacker gets ciphertext + can delete).

- **Questions for the future audit.** (1) Is the loopback publish of 9000 needed at all, or can it be dropped to bridge-only to remove the host-local raw-S3 surface? (2) Are the MinIO root credentials reused anywhere else, and what is the blast radius of their leak beyond "read/delete ciphertext"?

### 2.9 Deployment posture: disposable test server, single DOMAIN flag, destructive prod cutover

- **What it is** (`server/deploy/README.md`, `server/deploy/nginx/render-relay-conf.sh`, `server/docker-compose.yml:66-72`). One flag, `DOMAIN`, flips the whole hardening surface: empty = solo/IP/self-signed/no-HSTS/`MINIO_SECURE=false`; set = domain/Let's-Encrypt/HSTS/`MINIO_SECURE=true` (`render-relay-conf.sh:5-13`, `README.md:211-218`). The current test relay is treated as disposable, and the Phase C "cutover" is explicitly destructive — `docker compose down -v` wipes all state + blobs + logs, "Acceptable car pré-publication, zéro vrai utilisateur" (`README.md:319-373`).

- **Affirmative case.** Collapsing the IP→domain hardening into *one* flag prevents partial-hardening drift (HSTS on but MinIO plaintext, or vice versa) — a common ops footgun. Treating the test server as disposable *is itself the motto applied to ops*: there is no precious long-lived state to protect because there is no real user data yet, and the destructive cutover guarantees the old owner-based (identity-leaking) schema is gone clean rather than half-migrated. The post-cutover acceptance test (`README.md:394-407`) is an *adversarial self-check*: grep the live state for identity fields and the logs for public keys, asserting zero — the design verifies its own blindness.

- **Why this implementation (alternatives rejected).**
  - *Separate flags for cert/HSTS/MinIO-TLS.* Rejected — drift risk; one flag is misuse-resistant.
  - *In-place schema migration old→Phase-C.* Rejected (`README.md:331-334`) — the schemas are incompatible and a migration would risk carrying identity residue forward; a clean wipe is safer for the motto.
  - *Keep the test server's state across the cutover.* Rejected — pre-publication, zero real users, so wiping costs nothing and guarantees cleanliness.

- **Adversarial stress.** *"'Disposable' is fine pre-publication, but the same scripts and posture will carry into prod with real witnesses. The backup story is the weak seam: the README itself says off-host backups are 'recommended' and the memory notes the systemd backup timer was **never actually deployed on Vultr**. So a VM loss today loses everything, and a destructive `down -v` run against the wrong IP is a foot-gun the runbook warns about precisely because it's easy."* **Concession — this is the domain's softest spot.** The README has heavy guardrails (confirm-the-IP step, mandatory pre-flight backup, restore-refuses-non-empty-without-`--force`, `README.md:338-345, 296-297`), and the systemd timer + backup/restore scripts exist (`frappuccino-backup.timer`, `backup-state.sh`, `restore-state.sh`). But existence ≠ deployment: the off-host push is a *manual cron example* (`README.md:262-268`), not wired, and the daily timer's actual installation is operator-dependent. For a state that includes the *auth registry* (the one identity-bearing file), backup is a double-edged sword anyway: it durably copies the residual identity ledger off-host, so backup hygiene (encryption, retention) becomes a privacy control, not just a DR control — and the README flags backup encryption as "amélioration future, hors phase test" (`README.md:75`).

- **Assumptions & residual.** Rests on the operator actually installing the timer and wiring off-host push, and on the destructive cutover being run against the right host (human-gated). Does **not** claim automated, encrypted, off-host backups are in place — they are documented intentions.

- **Questions for the future audit.** (1) For a *production* deploy with real witnesses, what is the backup confidentiality story — is the state tarball (which contains the identity-bearing `.ratchet_registry.json`) ever written/transmitted unencrypted? (2) Is the SPKI-pin-vs-cert-rotation coupling (`README.md:41-93, 297-304`) operationally safe — does any normal cert renewal silently change the SPKI and brick pinned field devices?

### 2.10 Single-worker invariant, hardened container, bounded/scrubbed logging

- **What it is** (`server/Dockerfile:1-81`, `server/docker-compose.yml:97-128`, `server/app/logging_setup.py`). `--workers 1` is explicit and load-bearing (process-local nonce cache; multi-worker = replay bypass, `Dockerfile:42-48`). The container runs non-root (UID 1001), `read_only: true`, `cap_drop: ALL`, `no-new-privileges`, `tmpfs /tmp` (`docker-compose.yml:97-104`). Logs are JSON, IP-scrubbed (blocklist of `client_ip/remote_addr/...`, `logging_setup.py:46-60`), traceback-scrubbed to the exception class name only (`logging_setup.py:105-117`), with uvicorn.access fully disabled (`logging_setup.py:141-143`) and bounded by docker json-file rotation (`docker-compose.yml:20-24`).

- **Affirmative case.** The single-worker constraint is what makes the cheap, dependency-free process-local state (nonce cache, jwt blacklist, registries) *correct* — it trades horizontal scale (not needed at field volume) for the ability to reason about replay/budget atomicity under one lock. Container hardening means an RCE in the relay yields a capability-stripped, read-only, non-root process that cannot escalate or write the app dir. Log scrubbing is the *operational* half of "une saisie n'expose rien": a seizure of the container's json-file logs must not yield the identity↔activity link, so IPs, tracebacks (whose frame locals could `repr()` a pk/nonce, `logging_setup.py:105-111`), and public keys are all stripped (every enroll/auth/rotate log says "no pk," e.g. `auth_v2.py:161-163, 260-261, 361-363`).

- **Why this implementation (alternatives rejected).**
  - *Multi-worker for throughput.* Forbidden until Redis-backed shared state exists (`Dockerfile:42-48`, `.env.example:24-31`) — replay safety depends on a single cache.
  - *Plain-text human logs / default uvicorn access log.* Rejected — default logs the client IP (`logging_setup.py:8-13`); the custom JsonFormatter + access-log-off is the IP-leak fix (M-09).
  - *python-json-logger dependency.* Rejected (`logging_setup.py:27-30`) — "~50 lines of custom code" beats auditing an external dep for a pre-audit posture (surface minimization).
  - *Root container.* Rejected (`Dockerfile:1-9`) — non-root bounds an RCE.

- **Adversarial stress.** *"Single-worker is a self-inflicted availability bottleneck: one slow fsync or a wedged event loop and the *entire* relay is down (no second worker to absorb). For a tool whose whole point is 'get data off the phone fast,' the drain being a single process is a DoS magnet."* **Rebuttal, partial.** The design anticipated exactly this: all disk I/O in the hot paths is offloaded via `asyncio.to_thread` so fsync+rename don't block the event loop (`atomic_io.py:58-66`, `auth.py:316-345`, every `auth_v2.py` mutation), and a healthcheck restarts a wedged-but-"up" container (`docker-compose.yml:105-125`). The residual is genuine: throughput ceiling = one worker. The mitigation is field-scale (a handful of witnesses, not millions) + nginx buffering-off streaming + the client's own circuit-breaker/retry. The honest concession: this scales to the *current* threat model's user count, and the Redis migration is the documented unlock for beyond that.

- **Assumptions & residual.** Rests on field volume staying within one worker's capacity, on `to_thread` keeping the loop responsive, and on the healthcheck catching wedges. Does not claim horizontal scalability — it explicitly defers that to a future Redis migration.

- **Questions for the future audit.** (1) Is the `to_thread` offload comprehensive — is there any hot path that still does blocking disk/network I/O on the event loop (which under single-worker stalls *all* clients)? (2) Does any log call anywhere (including third-party libs: minio, slowapi, pyjwt, uvicorn) ever emit a client IP or a public key that the JsonFormatter blocklist doesn't catch (the blocklist is *name-based*, so a lib logging an IP in the *message string* would slip through)?

## 3. Domain coherence & tensions

The choices cohere around one disciplined idea: **the relay is trusted only for availability and anti-abuse, never for confidentiality or identity.** Confidentiality is delegated entirely to client-side E2E crypto (the relay holds ciphertext); identity is engineered *out* of the at-rest surface wherever anti-abuse permits. The report path achieves true identity-freedom (capability addressing, no owner/createdAt, token-free reads). The auth path *cannot* — replay and sybil prevention need per-identity state — and the design is honest about this, marking the ratchet registry and authorized-keys set as known "résidu §6" (`deploy/README.md:434-435`).

The central internal **tension** is exactly there: **anti-abuse vs. identity-freedom.** Every place the relay retains identity at rest (the long-term `ed25519_pk` in the registry, its `enrolled_at`/`updated_at`, the per-batch creation counters) exists to stop replay or sybil, and each was deliberately minimized (counters dropped on rotation, `ratchet_registry.py:232-238`; no pk in logs; report counts are numbers not maps). The unresolved question is whether the *minimum* anti-abuse state still concedes more than the motto can bear — specifically the **absolute timestamps** in the registry, which are arguably beyond what replay/sybil strictly require.

A second tension is **availability vs. simplicity/security**: single-worker + process-local state is what makes the anti-replay and budget logic provably atomic and dependency-light, but it is also the relay's hard scaling ceiling and a single failure point. The design accepts this for field-scale and documents the Redis exit.

A third, cross-cutting one: **at-rest blindness is strong, on-path blindness is delegated.** The relay scrubs everything it stores and logs, but it must terminate TLS and see a client IP to rate-limit. Metadata resistance against a network-position adversary therefore lives in the transport domain, not here — and that is the cleanest hand-off to the next audit.

## 4. Top-3 questions this domain hands to the future adversarial audit

1. **The auth registry is the one at-rest identity residual — is it minimal?** On seizure of `.ratchet_registry.json` (long-term pks + `enrolled_at`/`updated_at` + per-batch creation counts), how much of a per-identity activity ledger is reconstructable, are the absolute timestamps actually required for replay/sybil prevention, and can `reports.json` be re-joined to an identity via timing/ordering/count correlation despite the report side being identity-free?

2. **Blast radius of a `JWT_SECRET` compromise, and is the secret reachable via backups?** Confirm that a forged HS256 stream JWT (without any per-report key) can do no more than budget-bounded report creation — never decrypt, read the archive, or corrupt stored chunks — and verify `JWT_SECRET` is never written into the state tarballs / off-host backups (which, for the identity-bearing registry, are themselves a privacy surface that the README defers encrypting).

3. **Single-worker as both correctness anchor and availability single-point — and the unrate-limited PUT.** Audit for any hot-path blocking I/O left on the event loop (which stalls *all* clients under one worker), and confirm that the app-layer-unauthenticated `PUT /file/{report_id}/{filename}` is bounded only by nginx + the write-sig gate such that a flood of invalid-signature PUTs is rejected cheaply before any MinIO round-trip (write-once read-back amplification).
