## 1. Scope + threat model

The relay is a deliberately "blind" store-and-forward server: Android clients upload encrypted chunks over a pinned TLS channel; a rescue device later re-derives its identity from a BIP-39 phrase and pulls its own blobs back. Five adversaries are in scope, in roughly increasing capability: **(a) on-path ISP / state / hostile-WiFi observer** on the client uplink — sees TLS packet metadata (client IP, destination, timing, sizes) but never plaintext or app state; **(b) hosting provider / Vultr** — controls the hypervisor, can snapshot VM RAM and disk, sits in a US (CLOUD-Act) jurisdiction; **(c) relay operator** — root on the host, can read every file, log and Docker volume, and could *modify* code to start logging; **(d) server-seizure / law-enforcement actor** — offline disk image + VM snapshot of `/state`, MinIO volume, Docker logs, and any on-host backups; **(e) backup holder** — whoever receives `backup-state.sh` output (today: local on-host only; off-host rsync.net/B2 is ROADMAP 1.8, not yet done). The militant premise: **content secrecy is necessary but not sufficient.** "This device filmed 47 chunks on 2026-05-20 14:23 UTC and again the next morning" is, on its own, enough to corroborate a raid or place a person at an event. Metadata is the attack surface.

## 3. THE IP QUESTION — resolved definitively

**Question:** nginx `access_log` is off — but does the app, slowapi, the logging stack, or an exception path capture the forwarded `X-Real-IP`/`X-Forwarded-For` anywhere persistent?

**Answer: No, not in the deployed code.** The client IP is *extracted into process RAM* for rate-limiting and is *never written* to any log, file, or backup. Evidence, all from the live worktree tree:

1. **nginx writes no access log and injects the IP as a header only.** `access_log off;` and `proxy_set_header X-Forwarded-For $remote_addr;`, both in `server/deploy/nginx/relay.conf.template` (cited by directive: the line numbers this document used had already drifted by ~11 lines). The header travels to the backend; it is not persisted by nginx.
2. **uvicorn access logging is off three ways.** `--no-access-log` on the CMD (`Dockerfile:79`); and at runtime `setup_logging()` sets `uvicorn.access` `handlers=[]`, `propagate=False`, `disabled=True` (`logging_setup.py:134-136`). `main.py:17` calls `setup_logging()` at import, before any logger is used.
3. **The app's JSON formatter has an explicit IP blocklist.** `{client_ip, remote_addr, forwarded_for, x_forwarded_for, ip, host}` are dropped from any `LogRecord` (`logging_setup.py:55-60`). So even a careless `logger.info(..., extra={"client_ip": ...})` is silently stripped.
4. **No code reads the IP.** A grep of `server/app` for `request.client`, `request.headers`, `request.url`, `remote_addr`, `x-forwarded-for` returns **only** the single `get_remote_address` *key-func* registration on the shared limiter (`ratelimit.py:30`) — i.e. the IP is used solely as a slowapi bucket key, passed to no logger. Every `logger.*` call that includes identity logs a **truncated** `ed25519_pk[:16]` (e.g. `auth_v2.py:157,250,346`), never an IP.
5. **slowapi state is RAM-only.** `Limiter(key_func=get_remote_address)` with default in-memory storage; the `{ip → counters}` map lives in the worker process and is lost on restart. It is in **no** backup (`backup-state.sh` archives only the two named volumes).

**Two honest residual caveats (both real, neither currently realized):**
- **(a) `request.client.host` *is* the real client IP in memory.** `--forwarded-allow-ips=127.0.0.1` (`Dockerfile:81`) tells uvicorn to trust nginx's `X-Forwarded-For`, so the IP is authentic and present on the `Request` object. A *future* `logger.exception("... %r", request)` or `logger.info("auth from %s", request.client.host)` would capture it — and would route to the json-file driver. The blocklist only filters *named* `extra` fields; it does **not** intercept an IP embedded in a positional message string. This is a code-discipline gap, not a current leak. **Recommend a pre-commit/lint rule banning `request.client` and `request` in log args.**
- **(b) `slowapi==0.1.9`'s `_rate_limit_exceeded_handler`** (registered `main.py:73`) returns a `429 JSONResponse` carrying the limit description string; in 0.1.9 it does not emit a logger record containing the client IP. I could **not execute** slowapi locally to print the source (not installed on this machine; pinned in `requirements.txt:7`), so this one sub-claim rests on the pinned version's known behavior rather than direct local inspection — **flag for the auditor to confirm against the deployed wheel.** Even if it did log, controls #2–#4 mean nothing with an IP reaches disk via the app logger.

**Why several input findings rated this HIGH and were wrong for the *deployed* server:** they inspected `C:\…\Frappuccino\server\app\main.py` — the **stale `main`-branch root**, ~40 commits behind — where `main.py` uses `logging.basicConfig(...)`, there is no `logging_setup.py`, no `jwt_blacklist.py`, no `archive.py`, and the Dockerfile lacks `--no-access-log`. That tree is **not deployed**. The live tree is the `xenodochial-morse` worktree (per project memory, the tip therealshulgin runs). The refutations that hinge on "live server uses basicConfig" or "`--access-log` enabled" are **false for production** and true only for an abandoned branch. **The auditor should pin their review to the deployed commit and ignore the root `server/` tree** (or it should be deleted to remove the trap — see §7).

**Verdict on the IP question: CONTROLLED.** Client IP does not persist anywhere on the relay today. The unavoidable IP exposure is the **TLS handshake on the wire** (§2 #1), which no server-side setting can erase.

## 4. THE "WHEN YOU FILM" SIGNAL — recording-timeline reconstruction

This is the **highest-value militant risk**, and it survives full content encryption. There are two independent channels:

**(A) On-the-wire (adversary = ISP / Vultr, no server access).** The mobile client hard-pins a single destination, reached **by domain name** since 2026-06-27 (`DEFAULT_SERVER_URL = "https://relay.shake-document-protect.org:8443"`, `StreamRecordingService.kt`; the Rust verifier compares the host name the client is connecting **with** against `PINNED_HOST` and refuses any mismatch (`pin.rs`), which locks the app's own URL onto that domain rather than validating anything the server returns). So the observer sees a DNS lookup and a cleartext SNI on the control plane, on top of the fixed destination IP. Chunks themselves now default to ObfQuic on UDP `:8445` rather than through nginx (`RustUploadTransport.kt`), where Salamander hides the handshake from passive DPI but not the burst envelope, and not from anyone holding the APK's PSK. Therefore *the mere act of a TLS connection to that IP marks the user as a Frappuccino uploader.* Chunks are ~1.7 MB encrypted, emitted on a regular cadence during recording; with `proxy_request_buffering off` / `proxy_buffering off` (`relay.conf.template`, cited by directive) the upload streams through without server-side coalescing when the TCP path is used, so the **burst envelope on the wire closely tracks the recording envelope**. An on-path observer who never breaks TLS can infer: *that this client is uploading, when a session starts and stops, its duration, and its rough bitrate/volume* — purely from packet timing and sizes against a fixed destination. This is unavoidable without a VPN, Tor, or a domain-fronted/hidden-service front end. **It must be stated as a non-claim, not "fixed."**

**(B) On the server (adversary = operator / seizure / backup).** Even with zero IP logging, the persisted metadata reconstructs a recording timeline — but **Phase C unbound it from a stable identity at rest**:
- **Phase C: `reports.json` no longer carries `owner_pk`/`createdAt`** — the identity↔report↔"when" join is gone. The "when" survives only as the inherent MinIO object `last_modified` (next bullet); a report's blobs still group by `report_id`, but `report_id` is a phrase-derived capability, not a pk.
- MinIO `last_modified` per `<report_id>/<sessionId>_<seq>.strm` (`storage.py`) gives the **full intra-session cadence** and end time; chunk sizes give the volume/bitrate fingerprint.
- `ratchet_registry.json` `consumed_indices`/`batch_number` advances per auth — a session counter bound to the enrolled pk that increments **even though the blobs are undecryptable** (residual §6.2).
- **The hourly audit CSV is an explicit, ready-made activity time-series:** `/var/log/frappuccino-audit.csv` appends eight columns (`ts,records,minio_dirs,has_content,blobless_records,orphan_minio,blobs,bytes`) every hour (the `csv` branch of `audit-reports-vs-blobs.sh`, cron). It contains **no pk and no IP** (good), but `blobs_total`/`bytes_total` over time is a population-level "filming happened in this hour, this much" graph that persists with no rotation. It used to be cross-referenceable with a `createdAt` in `reports.json`; that field is gone from the schema, and `reports.py` names it as one of the two fields whose re-introduction would break the motto.

**Net (Phase C):** content is sealed AND the at-rest identity link is removed. What remains reconstructable from server state is **"*some* capability filmed at T1, T2, T3 for these durations/volumes"** (per `report_id`, not per pk), plus the enrolment registry's per-pk session *counters*; and from the wire, **"this IP was uploading to the relay at these times"** (the hard residual, §4A). The 6-month retention (§6) widens the server-side window to half a year. The pk↔report join that once made this "*this identity* filmed" no longer exists at rest.

## 5. EXPOSED-BY-DESIGN / honest non-claims

These are not bugs to "fix"; they are structural truths the threat-model docs (ROADMAP 8.1.5) must state plainly so no one over-trusts the relay:

- **The destination is a single fixed IP, now reached by name.** The client pins the **domain** `relay.shake-document-protect.org` (`pin.rs`, `network_security_config.xml` `<domain-config>`), so there is a DNS lookup and a cleartext SNI on the control plane where there used to be neither. Connecting at all is a signal, and marginally more of one than before. *Non-claim: we do not hide that a user talks to the relay, and the domain migration traded a small amount of wire discretion for a working certificate story (§7-P3-7).*
- **Phase C removed `owner_pk` from `reports.json`.** The pre-Phase-C model stored the full ed25519 pk to match a re-derived key for archive auth; Phase C made archive reads **identity-free** (the `report_id` capability replaces the pk match), so `reports.json` no longer links a device's sessions at rest. The residual identity-at-rest is now only the **enrolment registry** (`ratchet_registry.json`: pk + counters, no report mapping — §6.2; the V1 `authorized_keys.json` index was **retired 2026-06-29**, write-only/redundant since the `is_key_registered` drop — revocation now lives entirely in the registry as `revoked=true`). *Non-claim: a server seizure still reveals, via the registry, that a pk enrolled and roughly how active it was — but NOT which reports it created.*
- **`title`/`description` no longer exist in `reports.json` (Phase C).** The pre-Phase-C boilerplate (`"Stream <sessionId>"` / `"V2 live stream"`) is gone with the rest of the report metadata. *Non-claim: n/a — the field was removed, not just sanitized.*
- **Vultr / US CLOUD-Act jurisdiction.** A US provider can be compelled to image the VM (disk + RAM). All of §2 #4–#9 is then exposed; only blob *content* stays sealed. *Non-claim.*
- **Backups are local-only and unencrypted today.** `backup-state.sh` writes plaintext tar.gz to `/opt/frappuccino/backups/` (`:163-182`); off-host (1.8) is not done. *Non-claim: there is currently no off-host DR, and the on-host tarball is a single seizure away from the full metadata dossier.*
- **Blob-name + size + mtime metadata is inherent to an object store.** MinIO must name and time objects to serve them (`storage.py:146-177`). *Non-claim: the encrypted store still leaks per-chunk size and timing.*

## 6. Reframing the ROADMAP claim "TTL 6 mois sans risque"

The current rationale (`config.py:30-43`, `blob_cleanup.py:8-23`) is **correct about content and incomplete about metadata.** Precise wording:

> **Blob retention: 6-month TTL (`ARCHIVE_BLOB_TTL_SECONDS`, default `180×24×3600`).**
> **Content risk — none, and TTL-independent.** Blobs are STRM E2E-encrypted; the keys are BIP-39-derived and never reach the server. A seized blob is undecryptable whether it is 1 hour or 6 months old. A short TTL adds **zero** content protection and actively harms the field workflow (intermittent coverage needs >24h to drain an upload queue — observed 2026-05-21, 39% chunk loss under a 24h TTL). Keeping 6 months for *content* is sound.
> **Metadata / legal risk — reduced by Phase C; a wire/registry residual subsists and grows with the TTL.** Phase C removed the `owner_pk ↔ report_id ↔ createdAt` record from `reports.json`. For the retention window the server still holds an **undecryptable, capability-keyed** timeline: per-`report_id` blob `size`/`last_modified` (`storage.py`) = "*some* capability filmed, when, how long, how much" — but no longer "*which identity*". The pk↔activity link survives only in the **enrolment registry** (counters, §6.2). A 6-month TTL still means a seizure/backup breach exposes up to 6 months of capability-level timing. `reports.json` records are reaped on `last_modified` (no `createdAt` to key on anymore).
> **Corrected claim:** *"6-month TTL carries no **content** risk (E2E-encrypted, key never on server). It carries a residual **metadata** risk that scales with the window: the relay retains a seizure-exposable, undecryptable, capability-keyed timing graph (per-`report_id` size/mtime) for up to 6 months — Phase C removed the identity link from `reports.json`, so it is no longer an identity↔timing graph at rest. The TTL is a deliberate content-availability vs. metadata-exposure trade-off, not a no-risk setting."*

Optional **relay-side** hardening (next render geste, not APK): route `error_log` to a dedicated short-retention logrotate (`create 0600 root root`, ~3d) or `stderr`→journald with `Storage=volatile`. Do **not** use `error_log off`/`/dev/null` — it blinds ops on real TLS/upstream crashes. *(Surface #2; 2026-06-30 cross-audit F-03.)*

**P2 — structural metadata minimization (design review for the auditor).**
5. **Client-side encrypt `title`/`description` — DEFERRED 2026-06-04 (premise not met).** The premise is gone in a stronger way than when this was written: `title` and `description` were **removed from the schema entirely** (`reports.py` header: "There is deliberately NO owner, NO author, NO createdAt, NO title"), so there is nothing left to encrypt. Client-side encryption (an FFI `archive_list_reports` decrypt path + `.so` rebuild + backward-compat) is over-engineering for boilerplate. Revisit only IF a user-entered title feature is added. *(Surface #5 — re-rated NON-ISSUE for current code.)*
6. **Decide an explicit metadata-retention policy distinct from blob TTL.** Today metadata lives as long as the longest blob (≤6mo). `createdAt` has since been removed from the schema altogether, which settles the precision question; what remains for the auditor to weigh is auto-expiring `reports.json` entries on a metadata-specific TTL — accepting it degrades rescue UX. *(Surfaces #5/#6, ties to §6.)*

**P3 — migration-specific, and a documentation trap to remove.**
7. **DNS + Let's Encrypt (1.2/1.3) — HALF DONE, and the predicted regression happened.** The domain half shipped 2026-06-27: the client now pins `relay.shake-document-protect.org` instead of the raw IP, so the hostname does go out in cleartext in the ClientHello, exactly the metadata regression this item warned about. Its operative advice was followed — the SPKI pin was kept, and there are now three of them (`pin.rs`). What is still open: **Let's Encrypt itself is not done** (the relay serves a self-signed cert, so the migration bought DNS-addressability, not CA trust), **ECH** remains the only real answer to the SNI and remains impractical without a CDN front (§8.A), and the domain must be treated as publicly linkable to this project. Keeping this item is the point: it is the one place where the document called a regression before it happened.
8. **MinIO block-storage migration:** the new volume holds the same blob-name/size/mtime metadata (§2 #6). Ensure the new block device is **encrypted at rest** (LUKS/host-level) and that detaching the *old* `frappuccino_minio_data` volume **securely wipes** it, not just unmounts — otherwise the migration doubles the seizure surface.
9. **Delete or clearly quarantine the stale root `server/` tree.** It uses `basicConfig` with no IP filtering and a Dockerfile without `--no-access-log`; it caused multiple input findings to mis-rate the IP risk as HIGH. Leaving it in the repo is an audit-integrity hazard — the external auditor must review **only** the deployed commit. *(Meta-finding from §3.)*

## 8. OSS solution landscape — ce qui peut nous aider (ne pas réinventer la roue)

État OSS vérifié 2026-06. Les exposures se rangent en **deux problèmes orthogonaux**, avec des familles d'outils distinctes — les outils réseau ne corrigent PAS la corrélation côté serveur, et inversement.

### 8.A — Wire / IP / « tu parles à CE relais » + enveloppe temporelle (surfaces #1, #4A — observateur ISP/État/Vultr)

Problème réseau. **⚠️ Tor RECALÉ (décision therealshulgin 2026-06-14)** : latence variable + débit + clunky = **incompatible avec un upload vidéo continu soutenu** (notre demande réseau). On vise du **rapide, prévisible, type VPN/obfuscation**. (`arti` 2.0 reste noté pour mémoire, mais hors profil.)

**Deux sous-objectifs distincts** (clé du sujet) : **(1) inclassifiable** — le DPI ne doit pas pouvoir dire « c'est Frappuccino/un proxy » ; **(2) destination non-reliable** — « tu parles à CE serveur = tu es un uploader » : c'est le **résidu dur**, qui exige soit une **foule** (front CDN partagé / VPN commercial multi-tenant) soit de la **rotation/mirroring d'IP** — orthogonal à l'obfuscation. Pas de repas gratuit.

Paysage OSS rapide-obfusqué (vérifié 2026) :

- **Hysteria2 / TUIC (QUIC) — candidat primaire.** Débit **quasi-max même sur réseau lossy/haute-latence** (congestion BBR) ⇒ *exactement* notre réalité terrain : l'obfuscation devient un **gain net de résilience d'upload**, pas une taxe. Se fond en HTTP/3. **`quinn` = QUIC en Rust** → colle au stack (rustls). Le caveat « UDP parfois bloqué → fallback TCP requis » est **traité** : le port réel est UDP `:8445` (pas 443), et le repli vers DirectTls est implémenté et instrumenté (`directtls_fallback` / `directtls_degraded`, `ffi/src/lib.rs` ; latch de mode dégradé dans `quic.rs`, ré-armé à chaque enregistrement). **✅ PoC 2026-06-14 (ROADMAP §10.9)** : ×6–×15 de débit upload vs notre baseline réelle sous perte — car **le client Android est en `cubic` (BBR indispo)** et l'upload est gouverné par le CC de l'émetteur (le téléphone) ⇒ QUIC/Brutal contourne le stack cubic-only ⇒ **gain de fiabilité terrain, pas qu'obfuscation**.
- **VLESS + REALITY + XTLS-Vision (Xray) — fallback TCP/443 + meilleure camouflage.** État de l'art DPI 2026 (marche où Tor/WG/OpenVPN/Shadowsocks sont bloqués) : REALITY mimique un *vrai* site TLS (handshake/cert volés) → indétectable, ~débit natif. Écosystème **Go** (Xray/sing-box) — pas Rust (embarquer sing-box ou ré-implémenter REALITY = coût).
- **AmneziaWG — option « plein VPN » simple.** WireGuard obfusqué (headers dynamiques + padding + déguisement DNS/SIP/QUIC), ~vitesse WG, self-host. ⚠️ caveat 2026 : blocage **au niveau AS** de certains datacenters (Hetzner/Russie) ⇒ l'IP/AS de l'endpoint compte.
- **ECH (RFC 9849, mars 2026)** — chiffre le **SNI** seulement. La tension domaine/SNI n'est plus une hypothèse de migration : elle est **actuelle** depuis le 2026-06-27 sur le plan de contrôle, et ECH en est la seule vraie réponse. Mais **uniquement avec un front CDN** (Cloudflare), qui termine le TLS (voit les blobs opaques + métadonnée) → ajoute CF au graphe. Self-host ECH **« encore limité »**. Pas la voie near-term. Sur le plan de **données**, le SNI est déjà soustrait au DPI passif par Salamander, ce qui n'est pas la même propriété : le PSK est dans l'APK.

**Avantage archi** : on maîtrise client (Rust) + relais et les blobs sont déjà E2E ⇒ le transport obfusqué = **défense-en-profondeur sur le fil**, sous le TLS-épinglé+STRM, et **pluggable** (toggle direct / QUIC-obfusqué / VPN selon réseau & menace).

### 8.B — Mixing temporel / adversaire global (hors near-term)

- **Nym mixnet** — la réponse *théorique* (Sphinx + cover-traffic). **Vérifié 2026 : 5-hop « too slow for streaming » ; fast-mode 2-hop perd le mixing** ⇒ incompatible vidéo continue. **Parqué R&D.**
- **Padding / cover-traffic applicatif** (cadence constante pour décorréler upload vs enregistrement) — partiel, **coûteux en données mobiles + batterie**. Un *knob*, pas gratuit.

### 8.C — Corrélation côté serveur (surfaces #5/#6/#9 — opérateur/saisie/backup)

État serveur : les outils réseau **n'aident pas**. Réponses = minimisation (déjà priorisées §7) :
- **Backup chiffré `age`** (P0-1) — **fait, et non-optionnel** : `backup-state.sh` refuse de tourner sans `FRAPPUCCINO_BACKUP_AGE_RECIPIENT` plutôt que d'écrire un dossier d'état en clair (WP-A3). Cette puce disait « à moitié câblé » et contredisait §7 P0-1 dans le même document. Résidu réel : la gestion de la clé `age` hors du relais, à régler avec l'off-host (1.8).
- **Coarsening `createdAt`** (heure, pas ms) + **bucketisation/padding des tailles de chunk** (casse le fingerprint bitrate #6) + **TTL métadonnée distinct du TTL blob** (§6/§7-P2-6).
- **OHTTP (RFC 9458)** — sépare « qui » (un relais voit l'IP, pas la requête) de « quoi » (la gateway voit la requête, pas l'IP). Implémentations OSS mûres : **crate Rust `ohttp-gateway`**, libs Go/C++, prod Divvi Up, et **travaux Guardian Project** (écosystème proche de Tella). Pertinent pour **délier l'IP de l'upload** sans Tor, MAIS : (a) requiert un **relais OHTTP non-collusoire** distinct de notre gateway, (b) orienté requête/réponse → **peu adapté à un gros upload streamé**. ⇒ option secondaire.

### Direction recommandée (par ROI) — le point 1 est LIVRÉ

1. **Transport rapide obfusqué — LIVRÉ, plus une recommandation.** ObfQuic est le mode par défaut des chunks (`RustUploadTransport.kt`), l'obfuscation Salamander est byte-compatible Hysteria2 (`salamander.rs`), le PSK est câblé en production et une garde de build refuse un APK compilé sans `--features quic` (`mobile/build.gradle`). Le repli DirectTls est en place. Ce qui reste **non tranché** est le sous-objectif (2) ci-dessus, *destination non-reliable* : la moitié dé-obfuscation de la topologie serveur **est** versionnée ici (`crypto-rs/obfs-proxy/`, avec son unité systemd qui épingle l'écoute UDP `:8445` vers le front `127.0.0.1:8444`) ; ce qui n'est **pas** dans le dépôt est la configuration du front Caddy h3 `:8444` lui-même, donc les affirmations sur cette dernière ne sont vérifiables que contre le relais vif. Pour mémoire, l'alternative écartée était un fallback TCP/443 type VLESS+REALITY. Rapide + prévisible (≠ Tor, recalé), **gain de résilience réseau en plus** de l'obfuscation (BBR sur réseau lossy), pluggable (toggle). ⚠️ ne couvre que le sous-objectif (1) inclassifiable ; la **destination non-reliable (2)** reste à trancher (front partagé vs rotation IP).
2. **Backup `age` fini + non-optionnel (P0)** + **minimisation serveur** (coarsening ts, padding tailles, TTL métadonnée) = cheap, in-house, gros gain anti-corrélation.
3. **AmneziaWG** = alternative « plein VPN » obfusqué simple ; **OHTTP** (crate Rust) = IP-unlink secondaire (relais non-collusoire) ; **ECH** = pour la tension domaine/SNI, avec front CDN.
4. **Tor / Nym / mixnets** = **recalés/parqués pour notre profil** (latence/débit incompatibles avec l'upload vidéo continu).

**Allié OSS naturel** : **Guardian Project** (Orbot/Tor Android, OHTTP, concealed-auth) — proche de l'écosystème Tella/Horizontal dont Frappuccino est un fork ; à solliciter plutôt que réimplémenter.
