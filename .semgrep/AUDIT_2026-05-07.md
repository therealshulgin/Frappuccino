# Manual audit of `PinAttemptTracker.recordFailure` call-sites — 2026-05-07

Phase 4.2.3 of `ROADMAP.md`. RT-09 from
`BLUE_TEAM_COUNTERAUDIT_2026-04-21.md` (non conserve au depot)
flagged a potential miswiring: any Kotlin call-site that catches
`FfiException.WrongPin` AND feeds `PinAttemptTracker.recordFailure(...)` is
exploitable — an attacker injecting a corrupted blob into the stream can
push the user toward PIN lockout without any wrong-PIN attempt.

The semgrep rule [`frappuccino-pin-tracker.yaml`](frappuccino-pin-tracker.yaml)
encodes the pattern. Run it via `semgrep --config .semgrep/` once Phase 6.2.1
ships the CI workflow. Until then, this manual audit stands as the snapshot.

## Call-sites surveyed

`grep -rn "PinAttemptTracker\|FfiException" mobile/ stream-crypto/ --include="*.kt"`
(2026-05-07, branch `claude/xenodochial-morse` @ `fbcab3e`):

| File | Line | Context | Verdict |
|---|---|---|---|
| `mobile/.../PinAttemptTracker.kt` | (whole file) | Definition. Pure data structure + SharedPreferences I/O. No decryption logic, no FfiException handling. | OK |
| `mobile/.../PinUnlockActivity.kt` | 109 | `catch (e: FfiException.WrongPin)` after `pinStoreOpenExtended(pinStr, blob)` — true PIN unlock attempt. | OK — correct wiring |
| `mobile/.../PinUnlockActivity.kt` | 113 | `PinAttemptTracker.recordFailure(this)` inside the catch above. | OK — correct wiring |
| `mobile/.../ArchiveModeActivity.kt` | 79, 83 | catches `FfiException.InvalidMnemonicWord` / `InvalidMnemonic`, NOT WrongPin. No PinAttemptTracker call anywhere in the file. | OK — no exposure |
| `mobile/.../ArchiveModeActivity.kt` | 116 | bare `catch (e: Exception)` catch-all — would swallow WrongPin if a future decrypt flow lands here, but the catch body does NOT call `PinAttemptTracker.recordFailure` (it just renders an error to the screen). | OK — but watch when Phase 4.4 lands |
| `stream-crypto/.../ArchiveIdentity.kt` | (n/a) | Doesn't import PinAttemptTracker. Only handles archive-mode unseal of session keys. | OK |
| `stream-crypto/.../StreamUploadManager.kt` | (n/a) | Throws FfiException up to callers (StreamRecordingService, OnBoardSetPinFragment). Doesn't touch PinAttemptTracker. | OK |

## Conclusion

**RT-09 is not exploitable at HEAD `fbcab3e`.** The single
`PinAttemptTracker.recordFailure` call-site in the production code lives in
`PinUnlockActivity` and is gated by a true PIN unlock failure
(`pin_store_open*` round-trip), exactly as designed.

## Risk vectors going forward

1. **Phase 4.4 (archive retrieval)** will introduce streaming decryption from
   the server in `ArchiveModeActivity`. The new decrypt path will throw
   `FfiException.WrongPin` on AEAD failure (sealed envelope not for this
   identity, or tampered blob). Whoever wires it must NOT call
   `PinAttemptTracker.recordFailure` from that catch — render a
   "blob authentication failed" UX instead. The semgrep rule will fire if
   they do.

2. **Phase 4.3 (RT-09 fix proper)** will introduce
   `CryptoError::BlobAuthFailed` so the two failure modes stop sharing
   `WrongPin` at the type level. Once that ships, the runtime risk goes
   from "can be miswired by accident" to "miscompiles when miswired",
   which is the durable end state.
